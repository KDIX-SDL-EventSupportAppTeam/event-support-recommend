# このリポジトリの存在意義

## 一行で言うと

**第4回プロトフェス（2026-10-16 金）で、参加者が「自分では選ばなかったブース」へ足を運び、
それが新しい興味になるように仕向ける推薦サービス。**

---

## 成功の定義（これを外すと全部無意味）

> **踏破率でも、総訪問数でも、推薦の的中率でもない。**
> 参加者が**自分では選ばなかったであろうブース**を訪問し、
> それが本当に新しい興味・マッチングになること。

**人気ブースを全員に薦めれば踏破率は上がる。それは失敗である。**

この一文が本リポジトリのすべての設計判断を支配している。
評価指標を「当たった率」に置かないこと。

---

## 背景 — 去年、何が起きたか

第3回プロトフェス（2025-10-10・11）でもビンゴラリーアプリが運用され、
302名・2,114件のチェックインが記録された。そこには推薦機能もあった。

**しかし推薦は機能していなかった。** 原因はアルゴリズムの出来ではなく、**運用条件の設計ミス**である。

- 「チェックイン実績者が20人以下なら完全ランダム」というフォールバックが、
  **累計チェックイン約60件（1ブース1.5人）で解除**された
- 統計的にノイズでしかない段階で解除されたため、
  推薦は事実上**ブース人気度ランキングに退化**した
- その上位は**飲食ブースと制作チーム自身のブース**だった。
  誰にでも当たる推薦であり、研究目的に一切寄与していない

さらに構造的な欠陥があった。

- 訪問ブース数の中央値 **6.0** に対し、ビンゴの達成マス中央値は **3 / 16**。
  **訪問の半分がカードに載っていなかった**
- 推薦マスは中央4マス固定だったため、**推薦の効果と位置の効果が交絡**し、
  「+8.4ポイント」が何の効果なのか分離できない

**今年はこれらを構造で潰す。** ビンゴは動的段階解放方式になり、
推薦は「中央マスが2つ揃うたびに外周2マスを開放する」タイミングで呼ばれる。
どのマスが開くかは参加者ごとに違うので、**位置効果は構造的に消える。**

そして本リポジトリは、**フォールバックを早く解除しない**ことを仕組みとして持つ
（[03-phases.md](specs/03-phases.md)）。

---

## このリポジトリがやること

1. **候補ブースの順位づけ** — 参加者ごとに、全候補へスコアを付ける
2. **条件属性の算出** — (参加者, ブース) ペアの特徴量。分析リポジトリはこれを import する
3. **フェーズ判定** — データ量に応じて戦略を切り替える（`COVERAGE` / `SIMILARITY` / `DRSA`）
4. **DRSA 規則の生成とキャッシュ** — 5分ごとにバックグラウンドで
5. **研究用の生データの生成** — 推薦されなかった候補も含めた全候補のスコア

## このリポジトリがやらないこと

- **DB への書き込み** — 一切行わない。読むだけ
- **解放処理そのもの** — マスへの割当はサーバーの責務
- **指標の計算** — セレンディピティ率などは `event-support-analytics` の責務
- **UI への表示** — 推薦理由は記録するが画面には出さない（D-6）

---

## なぜ別リポジトリなのか

[サーバー側 ADR 0004](https://github.com/KDIX-SDL-EventSupportAppTeam/event-support-server/blob/develop/docs/decisions/adrs/0004-split-recommender-repository.md) の決定による。

- 実装言語が違う（Python / TypeScript）
- デプロイ単位が別（推薦は状態を持たないので複数インスタンス化できる）
- **分析と同じ言語で、特徴量の計算コードを共有できる。**
  「分析で使った定義と本番の推薦が違う」という研究上まずい事故を構造で防ぐ
- **推薦が落ちてもアプリ本体は動く**（タイムアウト＋フォールバック）。障害が隔離される
- 大学院での研究にそのまま持っていける独立資産になる

## 研究上の位置づけ

この推薦の効果測定は**セレンディピティの観測**である。

```
セレンディピティ率 =
    不一致カテゴリ（interest_match = MISMATCH）で推薦され、訪問し、高評価だった件数
  ÷ 不一致カテゴリで推薦された件数
```

対照群は「推薦なしの自発訪問（カード外訪問）」。
**これがないと「推薦されたから行った」のか「もともと行く人だった」のかを分離できない。**

そのため `scores` は**候補全件**を返す必要がある（分母になる）。
`interest_match` と `attributes` は**推薦した瞬間の値**として保存される
（カテゴリは運営が当日でも編集できるため、後から再計算すると別の値になる）。

> **手を抜いて `UNKNOWN` を返すと、研究データが丸ごと使えなくなる。**

**指標の計算自体はこのリポジトリの責務ではない。**
このリポジトリの責務は**「後から何度でも再計算できる生データを、正しく出すこと」**である。

## 動かせない前提

| # | 前提 | 出典 |
|---|---|---|
| 1 | **契約に合わせる側である。** 呼び出し元は実装・テスト済み。契約は変えられない | [ADR 0004（サーバー側）](https://github.com/KDIX-SDL-EventSupportAppTeam/event-support-server/blob/develop/docs/decisions/adrs/0004-split-recommender-repository.md) |
| 2 | **契約の内容をこのリポジトリにコピーしない。** リンクで参照する | 同上 |
| 3 | **単一イベント完結。** 過去イベントのデータを再利用しない（ブース構成が毎年変わる） | 恒久的な設計制約 |
| 4 | **評価は1人あたり 0〜3 件しか付かない。** 開場直後は全部 `null` | 契約 |
| 5 | **イベントは年1回、1日だけ。** 取らなかったデータは二度と取れない | — |
| 6 | サーバー側のタイムアウトは既定 **1000ms** | 契約 |
