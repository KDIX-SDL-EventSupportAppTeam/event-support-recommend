# ドキュメントの書き方

## 1. 日本語で書く

ドキュメント・コミットメッセージ・PR のタイトルと本文は**日本語**。

## 2. 置き場所

| 種類 | 置き場所 |
|---|---|
| 仕様（こうする、という定義） | `docs/specs/` |
| 判断の記録（なぜそうしたか） | `docs/decisions/adrs/` |
| 作業規約（守ること） | `docs/rules/` |
| 存在意義 | `docs/PURPOSE.md` |
| 索引 | `docs/README.md` |

**契約の本文は置かない**（[rules/contract.md](contract.md)）。

## 3. 状態を明記する

仕様ファイルの先頭に必ず置く。

```
---
状態: 草案 | 確定 | 実装済み
最終更新: YYYY-MM-DD
---
```

**「草案」と「確定」を区別する。** 草案を実装の根拠にしない。

## 4. 未決定は未決定と書く

**暫定値を確定値のように書かない。**

- 暫定なら「暫定」と明記し、**理由**（何が決まれば確定するか）を書く
- 未決定事項は `docs/README.md` の一覧に載せる
- **勝手に決めて実装しない。** 気づいたら手を止めて確認する

## 5. 数字には根拠を書く

しきい値・重み・既定値には、**なぜその値なのか**を必ず添える。

```
悪い: PHASE_DRSA_MIN=60
良い: PHASE_DRSA_MIN=60   # 条件属性2個 → 4×3=12 パターン × 各5件
```

根拠が無い数字は、後から変えてよいのか判断できない。
**根拠が弱いなら「根拠が弱い」と書く**（`PHASE_SIMILARITY_MIN=30` のように）。

## 6. 「起きてはいけないこと」を書く

仕様には「こうする」だけでなく、**「こうしてはいけない、破るとこうなる」**を書く。

このリポジトリは失敗の仕方が具体的に分かっている（去年の実例がある）。
**禁止と、その帰結を明示することが、仕様の主要な価値である。**

## 7. 更新のタイミング

| きっかけ | やること |
|---|---|
| 未決定事項が決まった | ADR を書き、仕様本体へ昇格させ、`docs/README.md` の一覧から消す |
| 条件属性の意味を変えた | `attributes.v` を上げ、[02-features.md](../specs/02-features.md) に**旧版の定義を残す** |
| サーバー側の実装で挙動を発見した | [01-io-contract.md](../specs/01-io-contract.md) §2.1 の「観測した事実」に追記する |
| 契約のズレを見つけた | `docs/README.md` の「サーバー側へ差し戻した事項」に追記する |

## 8. リンクは相対パスで

他リポジトリへのリンクは GitHub の URL を使う。
**本文をコピーせず、リンクする。**
