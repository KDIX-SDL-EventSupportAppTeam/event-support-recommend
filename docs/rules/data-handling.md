# データの扱い

## 1. 書き込まない

**このサービスは DB へ一切書き込まない。読むだけである。**

推薦結果の永続化はサーバーの責務（`recommendation_scores` / `card_unlock_events`）。
書き込まないことによって、**推薦エンジンの不具合がアプリのデータを壊せない**構造になっている。

読み取り専用の資格情報を発行できるなら、権限でも担保する
（[ADR 0002](../decisions/adrs/0002-決定表のデータ入手経路.md)）。

## 2. 取得してはならないもの

| 項目 | 理由 |
|---|---|
| `users.email` | 推薦にも分析にも不要。**渡さないことをもって事故を構造的に防ぐ** |
| `users.password_hash` | 同上 |

`user_id` は元から仮名なので、そのまま使ってよい。

## 3. スタッフの除外

**集計・推薦の両方で `users.role <> 'participant'` を除外する。**
運営スタッフと出展者は動作確認のために不自然なチェックインをする。

- 決定表の母集団から除外する
- フォールバック／`COVERAGE` の訪問者数集計から除外する

## 4. 去年のデータは使わない

**去年（第3回プロトフェス）のデータを推薦エンジンに食わせない。**

ブース構成が毎年変わるため、**単一イベント完結が恒久的な設計制約**である。
去年のデータの用途は、**今年の設計値を決めるための検証**に限られる
（それも Q-1 のように検証不能な項目がある。[ADR 0003](../decisions/adrs/0003-条件属性の構成.md)）。

## 5. ログ

**推薦1回につき、入力と出力の全体を JSONL で1行、標準出力へ吐く**
（[01-io-contract.md](../specs/01-io-contract.md) §5）。

- 保存先は Cloud Logging。**DB には書かない**
- サーバー側の書き込みが失敗しても、**こちら側に完全な記録が残る**
- メールアドレス等は §2 により取得しないので、ログにも入り得ない

**イベントは年1回、1日だけである。取らなかったデータは二度と取れない。**
取りすぎたログは無視すればよいだけなので、迷ったら出す。

## 6. テストデータ

- **合成データのみを使う。** 実データ・去年のデータをテストに使わない
- `data/` に個人データを置かない。**コミットしない**
- サーバーの `sample-data/generate.ts` はそのままでは使えない
  （`custom_answers` が UUID キー、`age_range` が日本語ラベル。
  [06 B-3](../specs/06-pre-survey-requirements.md)）

## 7. 分析リポジトリへ渡すもの

`features/` を import させる。**指標の計算はこちらでは行わない。**

分析側の規則（`event-support-analytics/docs/rules/data-handling.md`）が正本。
該当者が3名未満になる絞り込みでは集計を表示しない、等はそちらに従う。
