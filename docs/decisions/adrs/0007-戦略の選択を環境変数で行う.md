# ADR 0007 — 戦略の選択を環境変数で行う

- **状態:** 採用
- **日付:** 2026-08-31

## 背景

「アルゴリズムを簡単に切り替えられる設計にし、最初はランダム、あとからラフ集合へ」という進め方が提案された。
**現状を確認したところ、前半（切り替えの継ぎ目）は既に存在し、後半（ランダムから始める）は必要が無い。**

| 提案 | 現状 |
|---|---|
| 差し替え可能な設計にする | **済**。`strategies/base.py` の `Strategy` Protocol。`features/` `drsa/` も分離済み |
| 最初はランダムにしておく | **不要**。`COVERAGE` が実装済みで、人気順退化の禁止テスト（[07-testing.md](../../specs/07-testing.md) §1）を通っている |

**足りないのは戦略の実装ではなく、実行時に戦略を選ぶ口である。**
[engine.py](../../../src/event_support_recommend/engine.py) は `CoverageStrategy()` を直接生成している。

## 決定

### 1. `strategies/registry.py` を追加し、`STRATEGY` 環境変数で選ぶ

| 値 | 意味 |
|---|---|
| `auto`（既定） | フェーズ判定に従う。現状は必ず `COVERAGE` に落ちる（段3・4 未結線） |
| `coverage` | フェーズ判定を無視して `COVERAGE` に固定する |
| `random` | `RANDOM`（下限ベースライン）に固定する。**本番では使えない**（下記3） |

- `engine.py` は具象クラスを import せず、レジストリから解決する
- **未知の値は例外にせず `auto` として扱い、警告を起動ログに出す。**
  設定ミスでサービスが起動しないのは、このサービスの立ち位置（落ちても本体は止まらない）に対して過剰
- 段3・段4 で `SIMILARITY` / `DRSA` を実装したら、**レジストリに1行足すだけで済む**状態にする

### 2. `RandomStrategy` は「初期実装」ではなく「対照群」として置く

- **本番の既定にしない。** `COVERAGE` より悪いことが分かっているものを既定にする理由が無い
- 価値は比較にある。**`COVERAGE` がランダムより本当に良いのかを示す下限**として、
  [09-research-design.md](../../specs/09-research-design.md) の事前検証で使う
- **シードは `seed_for(user_id, unlock_context)` を使う。** グローバル乱数を使わない。
  同じ入力なら同じ出力（再現性）
- 全戦略共通の不変条件 S-1〜S-5 と、**人気順退化の禁止テスト P-1・P-4〜P-6 を必ず通す**
  （[07-testing.md](../../specs/07-testing.md) §1。P-2 は `COVERAGE` 限定なので対象外）

### 3. `STRATEGY=random` を本番で禁止する

`APP_ENV=production` かつ `STRATEGY=random` の場合は、**`auto` へ落として起動ログに警告を出す。**

理由は事故防止ではなく研究データの保護である。本番でランダムが混ざると、
**その時間帯の観測がどの戦略の結果なのか事後に判別できなくなる。**

### 4. JSONL ログに `strategy` を必ず出す

`phase` は契約で `COVERAGE` / `SIMILARITY` / `DRSA` の3値に固定されており、`RANDOM` を入れられない
（[01-io-contract.md](../../specs/01-io-contract.md)）。**契約を勝手に拡張しない。**

そこで `kind: "recommend"` のログに `strategy` フィールドを足し、
**レスポンスの `phase` とログの `strategy` を別物として扱う。**
`STRATEGY` を固定していた場合はログを見れば分かる。

## 理由

- 切り替えが env であれば、**Cloud Run のリビジョン切り替えとトラフィック分割がそのまま A/B の道具になる**。
  コード変更もデプロイのやり直しも要らない
- 当日の緊急退避手段が増える。`PHASE_DRSA_MIN` の引き上げ（[10-observability.md](../../specs/10-observability.md) §4）に加え、
  **`STRATEGY=coverage` で一段固定できる**

## 起きてはいけないこと

| # | 禁止 | 破ると |
|---|---|---|
| 1 | `RANDOM` を本番の既定にする | 品質を下げるだけ。**`COVERAGE` は既に動いている** |
| 2 | `RandomStrategy` を人気順退化テストの対象から外す | 「全戦略に同じテストを回す」原則が崩れる（[07-testing.md](../../specs/07-testing.md) §1） |
| 3 | `RANDOM` を `phase` として返す | 契約違反。サーバーの記録が壊れる |
| 4 | レジストリを `api/` に置く | 依存の向きが壊れる（[08-architecture.md](../../specs/08-architecture.md) §1） |
| 5 | `random.random()` などグローバル乱数を使う | 再現性が失われ、同じ入力の再実行で結果が変わる |

## 影響

- [11-deployment.md](../../specs/11-deployment.md) §3 に `STRATEGY` を追加した
- `.env.example` と [08-architecture.md](../../specs/08-architecture.md) §4 に追記が要る
- 段3・段4 の着手時、[ADR 0005](0005-段1と段2のみ実装する.md) の実装順序はそのまま。**登録先が1箇所に決まるだけ**
