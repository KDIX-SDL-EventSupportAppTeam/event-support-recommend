# ADR 0006 — 推薦サービスを未認証で公開する

- **状態:** 採用
- **日付:** 2026-08-31

## 背景

Cloud Run へ出すにあたり、サーバー（`event-support-server`）から推薦サービスへの呼び出しをどう認証するかを決める必要がある。

**観測した事実:** サーバーの `src/lib/bingo/recommenderClient.ts` は
`headers: { 'content-type': 'application/json' }` だけを付けて `fetch` している。
**`Authorization` ヘッダを送っていない。** つまり現在の実装のままでは、認証を要求した時点で呼び出しが全部失敗する。

## 選択肢

| 案 | 内容 | サーバー改修 | 判定 |
|---|---|---|---|
| a | `--allow-unauthenticated`。URL を知っていれば誰でも叩ける | 不要 | ⭐️ **採用** |
| b | Cloud Run IAM。サービスアカウントの ID トークンを付けて呼ぶ | **要** | ○ 最も堅い。時間があれば移行先 |
| c | 共有シークレットをヘッダで送る | **要** | △ b より弱く、手間は同じ |

## 決定 — 案 a

**`--allow-unauthenticated` で公開する。** ただし公開してよいのは `/recommend/cells` と `/health` のみ。

- `/ops/*` は `OPS_TOKEN` で保護する。**未設定のまま本番へ出た場合は素通しではなくルート自体を無効化する**
  （[11-deployment.md](../../specs/11-deployment.md) D-4）
- `/demo` は本番では登録しない（同 D-3）

## 理由

1. **変えたくない側を変えないため。** サーバーは実装・テスト済みである。
   [ADR 0002](0002-決定表のデータ入手経路.md) で案3を退けたのと同じ判断軸をここでも適用する
2. **守るべき資産が薄い。** 本サービスは **DB へ書かない**（[AGENTS.md](../../../AGENTS.md) 禁止5）、
   状態を持たない、氏名・連絡先を受け取らない。漏れて困る出力が無い
3. **落ちても本体は止まらない。** サーバーはフォールバックを実装済みで、
   `RECOMMENDER_URL` を空にすれば完全に切り離せる。**攻撃面としての価値が低い**

## 残るリスクと、それをどう扱うか

**「問題ない」ではなく「この2つが残る」と書いておく。**

| リスク | 深刻度 | 扱い |
|---|---|---|
| 計算資源の浪費（課金・インスタンス占有） | 低 | `--max-instances=4` で頭打ち。悪化時はサーバー側の `RECOMMENDER_URL` を差し替える |
| **偽リクエストによる JSONL ログの汚染** | **中。これが実質的な最大リスク** | 研究データが混ざる。`user_id` を DB の参加者一覧と突合して事後に除外する。**分析側の突合で落ちるので実装追加は不要** |

**このサービスにとって最も価値があるのは処理能力でも DB でもなく、当日の観測ログである。**
したがって未認証公開のリスク評価は「侵入されるか」ではなく「**記録が汚れるか**」で行う。
そして汚れても事後に落とせる。**だから許容する。**

## 前提条件（崩れたら再検討する）

- サービス URL を公開資料・スライド・リポジトリに載せない
- リクエストに氏名・連絡先が入る契約変更が起きない
- **書き込みを行う機能を追加しない。** 追加する場合は本 ADR を先に見直す

## 影響

- サーバー側の改修は不要。`RECOMMENDER_URL` に Cloud Run の URL を設定するだけ
- 案 b への移行は後からでも可能（サーバー側にヘッダ付与を足すだけ）。**本 ADR は b を否定しない**
