# ADR 0008 — パラメータ調整画面の置き場所とデモログの分離

- **状態:** 採用
- **日付:** 2026-08-31

[parameter-tuning/README.md](../../specs/parameter-tuning/README.md) の未決定 P-1・P-2 を決める。
Q-1（analytics 側の認証ヘッダ欠落）は本 ADR とは独立に必要な修正であり、§4 に対応方針だけ記す。

## 背景

`/demo` は推薦パラメータの調整プレイグラウンドである。検討の結果、次の2点が問題として残っていた。

| # | 問題 |
|---|---|
| P-1 | `/demo/run` が `run_recommendation()` を呼ぶため、合成 ID（`u_alice` 等）の推薦が `kind: "recommend"` として研究ログに混ざる |
| P-2 | 画面を推薦側に残すか、`event-support-analytics` へ移すか |

P-1 が未決のため、`/demo` は本番で 404 として塞いである（[11-deployment.md](../../specs/11-deployment.md) D-3。**暫定**）。

## 決定

### 1. デモ・リプレイのログを `kind` で分ける（P-1 = 案 a）

**「出さない」ではなく「区別できる形で出す」。** 誰がいつ何を試したかを後から復元できるほうが、
研究データとしての価値が高い。

- `run_recommendation()` に `log_kind: str = "recommend"` を追加し、`_log_recommend()` と
  context 構築失敗時の emit の両方に通す
- `/demo/run` は `log_kind="recommend_demo"` で呼ぶ
- **`/ops/replay` も `log_kind="recommend_replay"` で呼ぶ。** リプレイは保存済みリクエストを
  再実行するため *本物の* `user_id` で `recommend` 行を増やす。合成 ID と違い
  分析側の突合で落ちないぶん、`/demo` より危険である。同じ機構で同時に塞ぐ
- **本番の `/recommend/cells` は `"recommend"` のまま変えない。** 既存の分析経路に影響を出さない

分析側は `kind == "recommend"` だけを見ればよい。除外責務を分析側に持たせない。

### 2. `/demo` は推薦側に残し、`OPS_TOKEN` で保護する（P-2 = 案 A）

- **`/demo` は Streamlit ではない。** [demo.py](../../../src/event_support_recommend/demo.py) が
  HTML+JS を組み立て FastAPI が返す、依存ゼロの独立したページである。
  案 B（Streamlit へ移植）や React 化は、**同じ画面を得るために 760 行の書き直しと
  新しいビルド経路を増やす**ことになる。得るものが無い
- 「エンジニアが1箇所を見れば済む」目的は、**analytics の画面からリンク1本**で達成する
- 登録条件を `APP_ENV` から `OPS_TOKEN` の有無へ変える。`/ops/*`（D-4）と同じ形に揃える

| `APP_ENV` | `OPS_TOKEN` | `/demo` |
|---|---|---|
| production | あり | **登録する。`_require_ops()` で保護** |
| production | なし | 登録しない（404） |
| development | — | 登録する（保護なし。従来どおり） |

**「本番なのに秘密が未設定」を、素通しではなく機能停止で表現する**（D-4 と同じ原則）。

### 3. 本番設定を書き換える経路は作らない（X-1・X-2 の維持）

- `demo.py` の `_settings()` は呼ばれるたびに新しい `Settings` を組み立て、
  `app.state.settings` に触らない。**この構造を変えない**
- 画面上部に「これはシミュレータであり、本番設定は Cloud Run の env が正」を明記する（Q-5）
- [10-observability.md](../../specs/10-observability.md) §5 が「A/B の効果を当日見るな」と定めている。
  **見ながら変えられる画面は実験そのものを壊す**

## 帰結

- `/demo` が本番で使えるようになる。D-3 の「暫定 404」は解消し、記述を置き換える
- JSONL に `recommend_demo` / `recommend_replay` が現れる。[10-observability.md](../../specs/10-observability.md) §3 の一覧に追記する
- 秘密は2系統のまま（analytics の合言葉・推薦の `OPS_TOKEN`）。Q-4 を受け入れる
- [parameter-tuning/README.md](../../specs/parameter-tuning/README.md) を仕様本体へ昇格し、
  [docs/README.md](../../README.md) の未決定事項一覧から P-1・P-2 を消す

## 却下した案

| 案 | 却下理由 |
|---|---|
| P-1 b（`emit_log=False` で抑止） | 誰がいつ何を試したかが残らない。復元性を失うだけで得るものが無い |
| P-1 c（何もしない） | 分析側に除外責務を押し付ける |
| P-2 B（analytics の Streamlit へ移植） | 760 行の書き直しに対し、得るものはリンク1本との差でしかない |
| P-2 B'（React で書き直す） | ビルド経路・配信先・依存管理が新規に増える。現行 UI は素の JS で足りている |
| P-2 C（analytics が `strategies/` を import） | バージョンずれで「画面と本番の結果が違う」が起きる（X-3・[AGENTS.md](../../../AGENTS.md) 禁止2） |

## 積み残し（本 ADR の対象外）

**Q-1: `OpsStateClient.fetch()` が認証ヘッダを送っていない**（`event-support-analytics` の `src/rec_db.py`）。
D-4 で本番の `OPS_TOKEN` を必須にすると `/ops/state` が常に 401 になる。**analytics リポジトリ側の修正**である。

- ヘッダは **`X-Ops-Token` を使う。`Authorization` は使わない。**
  Cloud Run のプラットフォーム認証（IAM の ID トークン）が `Authorization` を使うため、
  将来 `/ops/*` を IAM で絞るときに衝突する。専用ヘッダなら層が分かれたままになる
  （推薦側の `_require_ops()` は両方を受け付けるので、選択は analytics 側の自由である）
- 401 だけは「取得不能」と区別して「認証エラー」と表示する。
  **さもないと「トークン設定漏れ」と「エンジンが落ちている」が当日画面で区別できない**
- ついでに Q-2（base URL がサイドバー手入力）も同じ修正で片付ける
