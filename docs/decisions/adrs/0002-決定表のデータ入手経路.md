# ADR 0002 — 決定表のデータ入手経路

- **状態:** **採用（案A′ — さくらプロキシの読み取り専用の口）**
- **日付:** 2026-08-29（起票） / 2026-09-01（決定）
- **関連:** `event-support-analytics` ADR 0001（同じ問題を先に解いた）、[ADR 0009](0009-当日の切り替えは既定値のまま走らせ調整は事後に行う.md)

**この ADR は当初「決定が必要であることを記録する」ものだった。2026-09-01 に決着した。**

## 背景 — 契約の穴

契約のリクエストには、**その参加者自身の訪問・評価しか入っていない。**

```
visited_booths: [ { booth_id, order, source, rating, rating_scale } ]   ← 最大3件、rating は 0〜3件
```

一方 **DRSA は全参加者の評価から規則を作る**手法である。
`SIMILARITY` も「属性が似た**他の**参加者が高評価したブース」を必要とする。

さらに `03-phases.md` のしきい値は明らかに**イベント全体の評価件数**を指している。

**現契約の入力だけでは `COVERAGE` しか実装できない。** ここは契約の穴である。

## 選択肢

| 案 | 内容 | 判定 |
|---|---|---|
| 1 | リクエストの情報だけで完結させる | ❌ `SIMILARITY` / `DRSA` を実装しないと同義 |
| 2 | 推薦エンジンが MySQL を読み取り専用で**直接**読む | ❌ **不可能。** さくら Standard は外部からの MySQL 直接接続を許さない |
| 3 | サーバーに決定表を渡す API を追加する | ○ 可。ただし実装・テスト済みのサーバーを改修することになる |
| **A′** | **さくらプロキシに読み取り専用の口を1つ足し、その鍵を推薦・分析の両方に配る** | ⭐️ **採用** |

## 決定（案A′）

`event-support-analytics` の ADR 0001 が同じ問題に先に決着をつけており、
**その決定と設置一式がそのまま本リポジトリの答えになる。**

1. さくら側に**読み取り専用の MySQL ユーザー**と、それに紐づく**プロキシの口**を1つ用意する
2. **その鍵を、分析リポジトリと本リポジトリの両方に配る**（鍵は分けない。利用者が2つになるだけ）
3. 本リポジトリは `data/` 層からその口を叩き、5分ごとに決定表を作り直す

設置手順・PHP・`grant.sql`・検証一式は
`event-support-analytics/deploy/sakura-readonly-proxy/` にある（先生への依頼はそこで完結する）。

### 当初の推奨（案2）を採らなかった理由

案2（MySQL 直接接続）は**そもそも成立しない**。本番はさくら Standard であり、
外部からの MySQL 接続ができない。この事実はサーバー側の
`docs/reference/environment-variables.md` に最初から書かれていた。
**回答が無かったのではなく、互いのドキュメントを見ていなかった。**

### 案3を採らなかった理由

- 変えたくない側（実装・テスト済みのサーバー）を変えることになる
- サーバーの Cloud Run は WebSocket のため `max-instances=1` に固定されている。
  当日ピークに、参加者のチェックインと同じインスタンスを決定表の集計が奪う
- 指標や属性を足すたびにサーバー改修とデプロイを待つことになる

## 与えられる権限

`grant.sql` が与えるのは以下の **SELECT のみ**。本リポジトリが決定表を作るのに過不足なく足りる。

| テーブル | 決定表での用途 |
|---|---|
| `check_ins` | 訪問の事実・訪問順・イベント絞り込み |
| `booth_ratings` | 決定属性（評価）。**これが決定表の本体** |
| `user_survey_answers` | 条件属性（関心分野・年代・職業）と SIMILARITY の近傍軸 |
| `booths` / `categories` / `booth_tags` | ブースの分類。`preference_match` の材料 |
| `bingo_cards` / `bingo_cells` / `card_unlock_events` | 提示の文脈（事後分析側で使う） |
| `users`（`id` と `role` のみ） | 出展者・運営の除外（`role='participant'`） |

**`users.email` と `users.password_hash` は権限の側で読めない。**

## 制約（この経路の性質。実装はこれを前提にする）

- **1リクエスト = 1SQL。** トランザクションも行ロックも無い
- **エラーはすべて HTTP 500 に潰れる。** MySQL のエラーコードは取れない
- したがって「何を試したか（どのテーブルか）」だけを例外に載せる。**SQL 本文と鍵は載せない**
- テーブル名・列名は定義から組み立て、`SELECT *` を書かない

## 影響

- `data/repository.py` の `UnavailableRepository` は開発・テスト用として残し、
  本番向けに読み取り専用プロキシ経由の実装を足す
- [ADR 0005](0005-段1と段2のみ実装する.md)（段1・段2に限る）の前提が解消される。**段3・段4 に着手してよい**
- 仕様は [specs/runtime-phase-switching/](../../specs/runtime-phase-switching/README.md) に書く

## 残る未確認

**さくら Standard で読み取り専用ユーザーとプロキシの口を追加できるかは、まだ確認できていない。**
追加できなかった場合は既存の DB ユーザーで動かし、書き込みは口の PHP 側の SELECT 判定だけで止める
（壁が2枚から1枚に減る）。**その場合も段3・段4 の実装は止まらない。**
