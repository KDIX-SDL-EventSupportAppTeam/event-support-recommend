# ADR 0002 — 決定表のデータ入手経路

- **状態:** **未決定（サーバー側の回答待ち）**
- **日付:** 2026-08-29

**この ADR は決定を記録するものではなく、決定が必要であることを記録するものである。**
決まるまで `SIMILARITY` / `DRSA` は実装しない。

## 背景 — 契約の穴

契約のリクエストには、**その参加者自身の訪問・評価しか入っていない。**

```
visited_booths: [ { booth_id, order, source, rating, rating_scale } ]   ← 最大3件、rating は 0〜3件
```

一方 **DRSA は全参加者の評価から規則を作る**手法である。
`SIMILARITY` も「属性が似た**他の**参加者が高評価したブース」を必要とする。

さらに `phases.md` のしきい値（決定表180件）は明らかに**イベント全体の評価件数**を指している
（評価回収率 × 累計チェックインで到達時刻を試算しているため）。

**現契約の入力だけでは `COVERAGE` しか実装できない。** ここは契約の穴である。

## 選択肢

| 案 | 内容 | 判定 |
|---|---|---|
| 1 | リクエストの情報だけで完結させる | ❌ **`SIMILARITY` / `DRSA` を実装しない**と同義。フェーズ設計が成立しない |
| 2 | **推薦エンジンが MySQL を読み取り専用で直接読む** | ⭐️ 推奨 |
| 3 | サーバーに決定表を渡す API を追加する | ○ 可。ただしサーバー（実装・テスト済み）の改修が要る |

## 推奨（案2）とその理由

- **[ADR 0004（サーバー側）](https://github.com/KDIX-SDL-EventSupportAppTeam/event-support-server/blob/develop/docs/decisions/adrs/0004-split-recommender-repository.md)
  が「分析と特徴量計算コードを共有する」ことを分割の根拠に挙げている。**
  分析側はテーブルを直接読む前提で書かれており、同じ `features/` モジュールを
  両方から使うなら、推薦側も同じ形のデータを扱えるほうが構造的に自然
- 決定表の構築は**5分に1回のバッチ**であり、リクエスト経路ではない。
  集計 SQL 1〜2本で足り、1000ms のタイムアウト制約とは無関係
- 案3は**変えたくない側（実装・テスト済みのサーバー）を変える**ことになる

## 決めるために必要な情報（サーバー側への質問）

1. **本番の DB アクセス経路。** サーバーはさくら上の PHP ラッパー API（`SAKURA_PROXY_URL`）経由で
   **1リクエスト = 1SQL、トランザクション無し、エラーは全部 500 に潰れる**。
   推薦エンジンも同じプロキシを叩くのか、MySQL へ直接接続してよいのか
   （Cloud Run → さくらの経路・IP 制限の有無）
2. **読み取り専用の資格情報を発行できるか。** 推薦エンジンは書き込みを一切行わないので、
   権限で担保したい
3. プロキシ経由になる場合、認証は `SAKURA_PROXY_KEY` の共有でよいか

案3を採る場合に必要なエンドポイントの形（参考。実装はサーバー側の判断）:

```
GET /internal/events/:event_id/decision-table
→ [{ user_id, booth_id, category_id, rating, rating_scale,
     age_range, occupation, interest_categories[], visitor_count }]
```

## この決定を待たずに進められること

**取得経路が変わっても層3（内部ドメインモデル）から見た姿は同一**になるよう、
`data/repository.py` の 1 インターフェースに抽象化してある
（[01-io-contract.md](../../specs/01-io-contract.md) §2.2）。

したがって次は先行して進められる。

- `COVERAGE` 戦略（層1の情報だけで完結する）
- `features/`（条件属性の計算。純関数）
- `drsa/`（DRSA コア。合成データでテストできる）

## 影響

- 決定するまで `SIMILARITY` / `DRSA` は**実装しない**
- 決まったら本 ADR を「採用」に更新し、選んだ経路と接続情報の扱いを記す
