# 条件属性の定義 — 決定表に載る特徴量

**このファイルが定義するものは、`event-support-analytics` との事実上の契約である。**

[ADR 0004](https://github.com/KDIX-SDL-EventSupportAppTeam/event-support-server/blob/develop/docs/decisions/adrs/0004-split-recommender-repository.md)
の決定により、**特徴量の計算は本リポジトリの1モジュール（`features/`）に置き、
分析側はそれを import する（コピーしない）。**
「分析で使った定義と本番の推薦が違う」という研究上まずい事故を、構造で防ぐためである。

したがって `features/` の関数シグネチャと戻り値は、**本リポジトリの公開 API** として扱う。
変更するときは §6 のバージョニング規律に従う。

---

## 1. 決定表の形

| 要素 | 内容 |
|---|---|
| **行（オブジェクト）** | **(参加者, ブース) のペア**。ブース単体ではない |
| **条件属性** | ペアの特徴。**すべて順序尺度**（DRSA の優越関係に必要） |
| **決定属性** | その参加者がそのブースに付けた評価（順序尺度） |
| **母集団** | そのイベントの `role = 'participant'` のみ。**スタッフ・出展者は除外する** |

```
user_id   booth_id   preference_match  rating_affinity   →  decision
u001      b012              3                 2          →  HIGH
u001      b027              1                 2          →  LOW
u002      b012              2                 3          →  HIGH
```

### 1.1 決定属性（決定クラス）

評価は `rating_scale` が可変なので、**スケール比で正規化してから2クラスに二分する。**

```
normalized = (rating - 1) / (rating_scale - 1)      # 0.0 〜 1.0

HIGH  … normalized >= HIGH_RATING_RATIO   （既定 0.75）
LOW   … それ以外
```

4段階なら `4 → HIGH` / `1,2,3 → LOW`。
DRSA は順序を持つ決定クラスを扱うので、上方union `>= HIGH` と下方union `<= LOW` を作る。

> **2クラスに絞る理由**: 決定表が最大でも数百件しかない。
> クラスを増やすとクラスあたりの件数が枯れ、規則が1人の気まぐれを写すようになる。

### 1.2 行に含める条件・含めない条件

| 条件 | 扱い | 理由 |
|---|---|---|
| 評価が付いている | **必須** | 決定属性が無い行は決定表に載らない |
| 参加者が事前アンケートに回答済み | **必須** | 未回答だと選好一致度が「0」ではなく**測定不能**になる。0 として混ぜると「宣言したが外れた」と区別がつかず、規則が濁る |
| 参加者が `role = 'participant'` | **必須** | スタッフは動作確認のため不自然なチェックインをする |
| カード外訪問（`cell_id IS NULL`）の評価 | **含める** | 推薦なしの自発訪問。学習データとして最も貴重（対照群でもある） |
| 事前推薦マス（`source = 'PRESURVEY'`）の評価 | **含める** | 決定表の行としては正当。ただし §3.2 の「行動由来の選好」の材料には**しない** |

> **今年はアンケート回答率がほぼ 100% になる見込みである。**
> 参加者の導線が「登録 → アンケート回答 → 完了画面 → アプリ」の一本道で、
> 回答しないとアプリ本体に入れないため。
> 去年は事後アンケート機能自体が無かったので、この点は構造的に改善している。

## 2. 属性設計の原則（なぜこの構成なのか）

> **参加者だけの属性は、同一参加者内で候補ブース間の値が変わらない。
> だからブースを順位づけできない。**

年代・性別・職業・参加回数・参加目的——これらはあるユーザーにとって全候補で同じ値になる。
ランキングに寄与せず、**規則の適用範囲を狭めてパターン密度を薄めるだけ**である。

条件属性になれるのは、**ブース側の属性と掛け合わせられるもの**に限られる。
そしてブース側に構造化データとして存在するのは、実質 `category_id` だけである。

| ブース側のデータ | 使えるか |
|---|---|
| `category_id` | ✅ **これが唯一の軸** |
| `booth_tags.tag` | △ 自由記述・正規化なし。契約のリクエストにも来ない（層2でのみ取得可） |
| `visitor_count` | ❌ 条件属性にしない。評価の予測力が弱く実質は人気度の裏返し。**同スコアの並べ替えにのみ使う** |
| `duration_band` / `knowledge_level` | ❌ D-12 により不使用。列は NULL のまま |
| `description` | △ 将来のテキスト特徴の余地。現時点では未使用 |

**年代・性別・職業を捨てるわけではない。** これらは条件属性ではなく
**SIMILARITY フェーズの類似度軸**と**事後分析の層別変数**として使う（[04-strategies.md](04-strategies.md)）。
「決定表には載せないが収集はする」という整理である。

## 3. 条件属性の定義

**既定で有効なのは A-1 と A-2 の2個。** A-3 は予備で、既定は無効
（[ADR 0003](../decisions/adrs/0003-条件属性の構成.md)）。

### 3.1 A-1 `preference_match` — 選好一致度（0〜3）

その参加者の選好と、ブースのカテゴリの一致度。**主属性**である。

宣言（アンケート）と行動（訪問）の2つの信号を足す。

```
D（宣言）= 2  ブースのカテゴリが top_interest_category と一致
          1  ブースのカテゴリが interest_categories に含まれる
          0  含まれない

B（行動）= 1  ブースのカテゴリが「FREE_VISIT で訪問したブース」のカテゴリと一致
          0  一致しない

preference_match = min(D + B, 3)
```

| D | B | 値 | 意味 |
|:-:|:-:|:-:|---|
| 2 | 1 | **3** | 第1希望であり、行動でも裏付けられている |
| 2 | 0 | **2** | 第1希望だが行動の裏付けはまだ無い |
| 1 | 1 | **2** | 関心分野に含まれ、行動でも裏付けられている |
| 1 | 0 | **1** | 関心分野に含まれるだけ |
| 0 | 1 | **1** | 宣言していないが、同種を訪問している |
| 0 | 0 | **0** | どちらの信号も無い |

**契約表との差分（意図的）**

契約の条件属性表は `0 = 明確に避けている` と定義しているが、
**本実装では `0 = 信号なし` とする。** 理由は2つ。

1. 「避けたい分野」を聞く設問が存在しない。判定の材料が無い
2. **聞くべきでもない。** 参加者に嫌いな分野を宣言させると、その分野を避ける方向に
   プライミングがかかる。本研究の測定対象はまさに不一致カテゴリへの訪問なので、
   **越えさせたい境界を自分で固める設問**になり、実験を汚染する

`attributes` はサーバーが解釈せずそのまま保存する不透明フィールドなので、
この読み替えはサーバー側に影響しない。ただし**分析側は本ファイルの定義を正とすること。**

**行動信号から `PRESURVEY` を除外する（重要）**

`B` の材料は **`source = 'FREE_VISIT'` の訪問のみ**とする。

position 5 の事前推薦マスは**こちらが推薦したブース**である。それを訪問したことを
「その人の興味」として数えると、**推薦が自分の事前推薦を再学習して増幅する閉ループ**になる。
契約のリクエストに `source` が入っているのは、この分離のためだと解釈する。

**1件目の訪問の扱い**

去年の初回訪問先は 1位 飲食 13.5% / 2位 制作チーム自身 10.9%、上位3件で 32.3%。
「会場に着いたら飲み物を買う」という生理であり、技術的興味を反映しない。

ただし解放1回目の時点で訪問は2件しかないため、**除外はしない。**
代わりに `B` を最大 1 に抑え、単発の訪問だけで属性が振り切れない設計にしてある
（`D` が 0 なら `B` があっても値は 1 止まり）。

### 3.2 A-2 `rating_affinity` — 評価履歴との親和度（1〜3）

その参加者の評価履歴と、ブースのカテゴリの関係。

```
3  高評価（normalized >= HIGH_RATING_RATIO）を付けたブースと同カテゴリ
2  そのカテゴリについて評価の情報が無い
1  低評価（normalized <= LOW_RATING_RATIO、既定 0.25）を付けたブースと同カテゴリ
```

高評価と低評価の両方に該当する場合は **2**（相殺）とする。

> **序盤はほとんどが 2 になる。** 評価は1人あたり 0〜3 件しか付かず、
> 解放1回目の時点では 0〜1 件である。この属性が効き始めるのは実質2回目以降である。
> **これは仕様であり、欠陥ではない。** 情報が無いときに 2（無関係）へ倒れることで、
> 属性が無根拠に順位を動かさない。

### 3.3 A-3 `exploration_disposition` — 探索志向（1〜3・予備・既定無効）

事前アンケートの自己申告をそのまま順序尺度として使う。

```
3  知らない分野も積極的に見たい
2  どちらともいえない
1  興味のある分野を中心に回りたい
```

**単独では参加者だけの属性であり、ブースを順位づけできない。**
価値があるのは `preference_match` との**交互作用**である。

> 「探索志向が高い参加者にとっては、選好一致度が低いブースでも高評価になりうる」

これが規則として抽出されれば、**このシステムの存在意義そのものを支持する証拠**になる。
一方、自己申告なので行動と一致しない可能性があり、
有効化するとパターン数が 12 → 36 に増えて必要件数も3倍になる。

**したがって「収集はするが、既定では決定表に載せない」。**
`ENABLED_ATTRIBUTES` で切り替える。判断は当日までのデータを見て行う。

## 4. `interest_match` — 契約の出力フィールド（条件属性ではない）

**条件属性とは別物である。混同しないこと。**
`preference_match` は決定表の列、`interest_match` は**セレンディピティ分析の分母を作るラベル**である。

| 値 | 定義 |
|---|---|
| `MATCH` | ブースのカテゴリが **`top_interest_category` と一致** |
| `PARTIAL` | ブースのカテゴリが `interest_categories` に含まれる（ただし第1希望ではない） |
| `MISMATCH` | ブースのカテゴリが `interest_categories` に**含まれない** |
| `UNKNOWN` | 事前アンケート未回答／関心分野が空／ブースに `category_id` が無い |

- **`MISMATCH` の定義が研究の要である。** Q-6 の暫定定義
  「事前アンケートで選ばなかった分類のブース」と一致させてある。
  分析側は `MATCH` と `PARTIAL` を合算すれば「宣言した分野」になる
- `top_interest_category` の設問が採用されなかった場合、`PARTIAL` は発生せず
  `MATCH` = 宣言した分野すべて、となる。**この場合も `MISMATCH` の意味は変わらない**
- **判定可能なのに `UNKNOWN` を返してはならない。** 研究データが丸ごと使えなくなる
  （[01-io-contract.md](01-io-contract.md) O-3）

### 凍結値であること

**カテゴリは運営が当日でも編集できる。** 後から再計算すると推薦時点とは違う判定になり、
分析が再現できない。したがって `interest_match` と `attributes` は
**推薦した瞬間の値をそのまま保存する。**

## 5. 使わないと決めたもの

| 項目 | 理由 |
|---|---|
| 混雑度・訪問者数 | 評価の予測力が弱く実質は人気度の裏返し。**同スコアの並べ替えにのみ使う**（空いているほうを優先） |
| ブースの `knowledge_level` / `duration_band` | D-12。出展者が自己申告しづらく、評価しづらい |
| 参加者の知識レベル | ブース側の相方（`knowledge_level`）が消えたため、掛け合わせる相手が無い |
| 年代・性別・職業 | 条件属性にはしない（§2）。SIMILARITY の類似度軸・層別変数として使う |
| 参加回数・参加目的・期待度 | ブース側に対応物が無く、順位づけに寄与しない |
| 過去イベントのデータ | ブース構成が毎年変わる。**単一イベント完結が恒久的な設計制約** |

## 6. バージョニング規律

属性は**後から変える前提**である（Q-1 は未確定のまま進む）。
そのため計算結果には必ず版を刻む。

```jsonc
"attributes": {
  "v": 1,
  "strategy": "DRSA",
  "enabled": ["preference_match", "rating_affinity"],
  "condition": { "preference_match": 3, "rating_affinity": 2 },
  "raw": { "declared": 2, "behavioral": 1, "category_id": "…", "visitor_count": 12 }
}
```

- `raw` に**組み立ての材料**を残す。これがあると、後から別の定義で再計算して比較できる
- 属性を足す・意味を変えるときは **`v` を上げ、本ファイルに旧版の定義を残す**
- **キー名の意味を後から変えない。** 変えるくらいなら新しいキーを足す
- 分析側が参照するのは `features/` の関数であり、**この JSON を自前でパースし直さない**

## 7. 分析側（`event-support-analytics`）への公開範囲

`features/` は **HTTP も SQL も FastAPI も知らない純関数の集まり**とする。
引数は素のデータ構造（dataclass / dict）に限る。

| 公開するもの | 用途 |
|---|---|
| 条件属性の計算 | 決定表の再構築、定義を変えた再計算 |
| `interest_match` の判定 | セレンディピティ率の再計算 |
| 評価の正規化とクラス分け | しきい値を変えた感度分析 |
| 属性の定義メタデータ（値域・順序の向き） | DRSA 以外の手法へ流用するとき |

**分析側はこれを import する。コピーしない。**
