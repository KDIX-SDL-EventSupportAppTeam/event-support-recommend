# 事前アンケートへの要求 — 推薦エンジンが必要とする設問

**このファイルは提案であり、決定ではない。**
事前アンケートの設問は `event-support-server` の `survey_questions` テーブルに属するデータであり、
決定権はサーバー側・運営側にある。本ファイルは**推薦エンジンという消費者からの要求**を示す。

**実質の締切はイベント当日ではなく、アンケートの配布日である。**
配布後に設問を足しても、既に回答した参加者からは取れない。

---

## 1. 現状（2026-08-29 時点で確認した事実）

| 事実 | 確認元 |
|---|---|
| 事前アンケートの器（配信 API・回答保存・公開ゲート）は**実装済み** | `routes/v1/survey.ts`、`docs/specs/pre-survey/` |
| フロントの設問ハードコード（旧8問）は**削除され**、サーバー配信に移行済み | `event-support-frontend` の履歴 |
| **本番の設問セットはどこにも存在しない。** 開発シードの `interest_categories` 1問のみ | `survey_questions` に投入なし |
| 年代のキーは **`age_range`**（`age_group` ではない） | `survey.ts` / `presurveyApi.ts` |
| 関心分野は `categories` から動的生成され、`category_id` の配列で保存される | P-10 / P-13 |

**つまり、いま設問を決めればそれがそのまま本番の設問になる。**

---

## 2. 設問を選ぶ基準

> **参加者だけの属性は、同一参加者内で候補ブース間の値が変わらない。
> だからブースを順位づけできない。**

詳細は [02-features.md](02-features.md) §2。この原則から、設問は2種類に分かれる。

| 種別 | 役割 | コスト |
|---|---|---|
| **(a) 条件属性になる設問** | 決定表の列。ブース属性と掛け合わせて順位を作る | **高い**。1個増えるとパターン数が3〜4倍、必要件数も比例して増える |
| **(b) 層別・類似度用の設問** | 決定表に載せない。SIMILARITY の近傍計算と事後分析に使う | **低い**。離脱リスクのみ |

**(b) を切り捨てる必要はない。** 年代・職業は条件属性としては弱いが、
SIMILARITY フェーズの類似度軸としては有効である（[04-strategies.md](04-strategies.md) §3）。

そしてブース側に構造化データとして存在するのは実質 `category_id` だけなので、
**カテゴリと掛け合わせられない設問は (a) になれない。**

## 3. 要求する設問（6問・うち必須5問）

### (a) 条件属性になるもの — 2問

| # | `question_key` | `answer_type` | 必須 | 選択肢 |
|---|---|---|:-:|---|
| 1 | `interest_categories` | `multi` | ✅ | `categories` から動的生成（P-10・既存） |
| 2 | `top_interest_category` | `single` | ✅ | 同上。1で選んだ中の第1希望 |

**2 が本ファイルで最も重要な要求である。**

現状の `interest_categories` は多肢選択なので、選好一致度は
**「一致 / 不一致」の2値にしかならない。**
契約の条件属性表は 3〜0 の4段階を求めているのに、アンケート由来の解像度が2段階しかない。

「一番興味がある分野を1つ」を足すだけで、
**条件属性の個数を増やさずに、主属性の解像度が 2段階 → 3段階に上がる。**
追加コストは1タップ、ブース側の新データも不要。費用対効果が突出している。

さらに、契約の出力フィールド `interest_match` の `PARTIAL` は
**この設問が無いと発生しない**（[02-features.md](02-features.md) §4）。

### (b) 層別・類似度用 — 4問

| # | `question_key` | `answer_type` | 必須 | 選択肢（`value`） |
|---|---|---|:-:|---|
| 3 | `age_range` | `single` | ✅ | `teens` / `twenties` / `thirties` / `forties` / `fifties_plus` |
| 4 | `occupation` | `single` | ✅ | `student` / `engineer` / `designer` / `planner` / `other` |
| 5 | `gender` | `single` | ⬜︎ 任意 | `male` / `female` / `other` / `prefer_not_to_say` |
| 6 | `exploration_disposition` | `single` | ✅ | `low` / `mid` / `high` |

**6 の文言案**: 「知らない分野のブースも見てみたいですか」
（`high` = 積極的に見たい / `mid` = どちらともいえない / `low` = 興味のある分野を中心に回りたい）

**6 も新規の要求である。** これは順序尺度で、**セレンディピティの調整変数**になる。

> 「自己申告で探索志向が低い層でも、推薦されると不一致カテゴリを訪問し、高評価した」

これが言えると、全体のセレンディピティ率だけを示すより格段に強い主張になる。
1タップで、**後から絶対に取れない**種類のデータである。

加えて、**予備の第3条件属性の最有力候補**でもある
（[ADR 0003](../decisions/adrs/0003-条件属性の構成.md)）。

## 4. 落とすことを提案する設問（旧8問案から）

| 落とすもの | 理由 |
|---|---|
| `attend_count`（参加回数） | ブース側に対応物が無い。順位づけに寄与しない |
| `purpose`（参加目的） | 同上。去年データが無いため層別比較にも使えない |
| `motivation`（期待度） | 同上。かつ回答が高値に偏る典型 |
| `knowledge_level`（知識レベル） | **ブース側の知識レベルが D-12 で不採用**になったため、掛け合わせる相手が存在しない |
| `free_comment`（自由記述） | 分析対象外と明記済み。必須でない設問で離脱を増やす |

必須7問 → **必須5問 + 任意1問**。
**アルゴリズムが実際に使うのは 1・2 の2問だけ**で、残りは1タップの層別変数、という構成である。
PQ-3（8問を3〜5問へ削る）の意図とも整合する。

## 5. 値の形式に関する要求

| 要求 | 理由 |
|---|---|
| `options` の `value` は**英語スネークの離散コード**、`label` が日本語 | 表示文言を変えても分析が壊れない。`02-data-model.md` の `{value, label}` 形式 |
| `question_key` を**必ず設定する** | UUID は環境ごとに変わる。分析側の識別子はこちらだけ |
| `interest_categories` / `top_interest_category` の `value` は `category_id` | ブースの `category_id` と直接突き合わせる |
| 締切後にカテゴリを編集しない運用が望ましい | 編集されると既存回答が存在しない id を指す。推薦側は凍結値で対処するが、回答自体は救えない |

## 6. 実装上の障害（サーバー側の対応が必要）

**現状、この設問セットを運営画面から作ることができない。**

| # | 内容 | 影響 |
|---|---|---|
| B-1 | `admin/survey-questions.ts` の `surveyBody` が `options: string[]` のままで、**`question_key` も `answer_type` も書き込めない** | 運営画面で作った設問は `question_key = NULL` になり、`survey.ts` の検証ループで**丸ごとスキップされる**＝推薦・分析から見えない。`multi` も設定できないので `interest_categories` を作れない |
| B-2 | 本番の設問セットが存在しない | 配布前に誰かが必ず作る必要がある。B-1 のため現状の手段は SQL のみ |
| B-3 | `sample-data/generate.ts` が `custom_answers` を **`question_key` ではなく設問 UUID キー**で書き、`age_range` に日本語ラベル（`'20代'`）を入れる | 生成したサンプルデータで推薦経路を検証できない |

**推薦エンジンとしては、B-1 が直らなくても
「マイグレーション or シードで設問を投入する」形であれば要求は満たされる。**
どちらの手段を採るかはサーバー側の判断に委ねる。

---

## 7. 要求のまとめ（最小限）

譲れない順に並べる。

1. **`interest_categories` が `category_id` の配列で入ること** — これが無いと推薦は
   ほぼ何もできない（事前推薦マスも常に空になる）
2. **`question_key` が設定されていること** — 無いと回答が読めない
3. **`top_interest_category`** — 主属性の解像度が2倍になる。1タップ
4. **`exploration_disposition`** — 研究上の価値が最も高い。後から取れない
5. `age_range` / `occupation` — SIMILARITY の近傍計算に使う
6. `gender` — 層別のみ。任意回答。**条件属性にも近傍計算にも使わない**
   （去年「その他」が3名。軸にすると個人を指しうる）
