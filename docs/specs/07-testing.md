# テスト方針

## 0. 方針

> **「起きるべきこと」より「起きてはいけないこと」を先に書く。**

推薦の良し悪しは正解が無いので、期待値を書くテストは書きにくい。
一方で**やってはいけないこと**は明確に決まっている。そこを固定する。

そして**評価指標を「当たった率」に置かない。**
人気ブースを全員に薦めれば当たった率は上がるが、それは失敗である。

**テストは3種類ある。**

| 種類 | いつ回すか | 目的 |
|---|---|---|
| 単体・契約（§1〜§7） | 常時（CI） | 実装が正しいか |
| **事前検証（§8）** | **イベント前に1回** | **アルゴリズムが目的を果たすか** |
| リハーサル（§12） | イベント前に1回 | 本番環境で動くか |

**§8 が本リポジトリ固有の重要部分である。** 単体テストは「部品が正しい」ことしか言わない。

---

## 1. 最重要 — 人気順への退化を禁じるテスト

**このリポジトリで最も重要なテスト群。** 全戦略に対して同じテストを回す。

| # | 固定すること |
|---|---|
| P-1 | スコアと `visitor_count` の順位相関（Spearman）が **正にならない** |
| P-2 | `COVERAGE` では順位相関が**明確に負**になる |
| P-3 | 訪問者数が突出したブースを1件混ぜたとき、それが `assigned` の先頭に来ない |
| P-4 | 全参加者に同じ推薦が返らない（属性が違えば結果が違う） |
| P-5 | `interest_term` の `MISMATCH` が 0 でない（不一致ブースが構造的に排除されない） |
| P-6 | 同じ `interest_match` を持つ候補どうしでは `visitor_count` 昇順に厳密に並ぶ |

**P-5 の意味**: 不一致カテゴリが決して選ばれない実装は、
セレンディピティを観測不能にする。**測定対象を消してしまう実装は失敗である。**

新しい戦略を足すときは、**まずこの節のテストを通すこと。**

## 2. 契約の遵守

サーバー側（`recommenderClient.ts`）が黙って捨てる・潰す挙動があるため、
**返したのに反映されない**事故が起きやすい。型で守れない部分をテストで固定する。

| # | 固定すること | 破ると起きること |
|---|---|---|
| C-1 | レスポンスのキーが **`decision_table_size`**（snake_case） | `null` として記録され、データ量と精度の関係が永久に分析できない |
| C-2 | `scores` の件数が `candidate_booths` と**必ず一致** | セレンディピティ率の分母が壊れる |
| C-3 | `interest_match` が 4 値のいずれか。**判定可能なのに `UNKNOWN` を返さない** | 研究データが丸ごと使えなくなる |
| C-4 | `assigned` が `cell_count` 以下 | 超過分はサーバーに捨てられる |
| C-5 | 返す `booth_id` がすべて `candidate_booths` 内 | 候補外はサーバーに捨てられる |
| C-6 | `score` が 0..1 に収まる | — |
| C-7 | OpenAPI スキーマが契約と一致（回帰検出） | 契約のズレに気づけない |

## 3. 通常の異常入力（すべて 200 を返す）

**開場直後はこれらが常態である。異常系ではない。**

| 入力 | 期待 |
|---|---|
| `pre_survey` が `null` | 200。`interest_match` は全件 `UNKNOWN`、実質「訪問者数が少ない順」 |
| `pre_survey` が `{}` | 同上 |
| `visited_booths` が `[]` | 200 |
| `rating` が全件 `null` | 200。`rating_affinity` は全件 2 |
| `candidate_booths` が `cell_count` 未満 | 200。`assigned` は足りないまま返す（埋めない） |
| `candidate_booths` が1件 | 200 |
| `cell_count` が 2 / 4 / 6 以外 | 200。範囲を丸めて処理する |
| `interest_categories` が存在しないカテゴリを指す | 200。該当なしとして扱う |
| スナップショットが未取得 | 200。`phase='COVERAGE'`、`decision_table_size=null` |
| 規則キャッシュが空 | 200。`SIMILARITY` 以下へ退避 |
| 未知のフィールドが増えている | 200。無視する |

**500 を返した時点でテスト失敗**とする（[01-io-contract.md](01-io-contract.md) O-6）。

## 4. フェーズ判定

### 境界値

| 入力 | 期待 |
|---|---|
| 29 / 30 | `COVERAGE` / `SIMILARITY` |
| 59 / 60 | `SIMILARITY` / `DRSA` |
| 0 | `COVERAGE`（例外を投げない） |
| 負数・NaN・None | `COVERAGE`（例外を投げない） |
| しきい値を設定で変更 | 即座に反映 |
| 属性3個構成 | `PHASE_DRSA_MIN` の既定が 180 |

### 品質ゲート（[03-phases.md](03-phases.md) §3.3）

| 入力 | 期待 |
|---|---|
| 件数は足りるが規則2本 | `SIMILARITY` に留まる |
| 件数・規則は足りるが γ = 0.4 | `SIMILARITY` に留まる |
| 件数・規則・γ は足りるが被覆率 0.3 | `SIMILARITY` に留まる |
| 4条件すべて満たす | `DRSA`。`quality_gate_passed = true` |

**起きてはいけないこと**: しきい値がコードに直書きされている／
決定表が空なのに `SIMILARITY` 以上を返す／**規則0本なのに `phase='DRSA'` を返す**。

## 5. DRSA コア

手計算できる小さな決定表で検証する（[05-drsa.md](05-drsa.md) §6）。

- 優越集合 `D^+` / `D^-` が手計算と一致
- 下方近似・上方近似・境界領域が手計算と一致
- `DRSA_CONSISTENCY = 1.0` で厳密版と一致
- 優越原理に反する行を足すと境界領域に落ちる
- 規則 id が再生成しても変わらない（安定 id）
- 生成が入力順に依存しない（決定性）
- 決定表が空・1行・全部同じクラスでも例外を投げない
- `support` が 1〜2 の規則が残らない

## 6. 条件属性（`features/`）

**分析側が import する公開 API なので、シグネチャの回帰も固定する。**

| # | 固定すること |
|---|---|
| F-1 | `preference_match` の 0〜3 が定義表どおり（D × B の全組合せを総当たり） |
| F-2 | **`source='PRESURVEY'` の訪問が行動信号 `B` に入らない**（自己増幅の防止） |
| F-3 | `rating_affinity` が `rating_scale` に依存せず正規化される（4段階・5段階で同じ結果） |
| F-4 | 高評価と低評価の両方に該当したら 2（相殺） |
| F-5 | `interest_match` の 4 値が定義どおり。`top_interest_category` が無ければ `PARTIAL` が出ない |
| F-6 | アンケート未回答の参加者が決定表に入らない |
| F-7 | `role != 'participant'` が決定表・訪問者数集計から除外される |
| F-8 | `attributes.v` / `enabled` / `raw` が出力に含まれる |

**F-2 は仕様書を読まないと絶対に気づけない**ので、テストで固定する価値が高い。

## 7. 実験設計（参加者内ランダム化）

[09-research-design.md](09-research-design.md) §2 の実装を固定する。
**当日を過ぎると検証できない**ので、テストで守る価値が特に高い。

| # | 固定すること |
|---|---|
| X-1 | **品質ゲート未通過のときは分割が発動しない**（全枠が現行フェーズの戦略） |
| X-2 | ゲート通過後、`cell_count` が 2 / 4 / 6 のとき各群が 1 / 2 / 3 枠になる |
| X-3 | 各 `assigned` の `attributes.arm` に `DRSA` / `COVERAGE` が入る |
| X-4 | 両戦略が同じブースを選んだとき、重複せず片方が次点へ送られる |
| X-5 | 割付が `hash(user_id, unlock 文脈)` で決まり、**同じ入力なら同じ割付**になる |
| X-6 | 参加者が違えば割付が散る（全員が同じ並びにならない） |
| X-7 | 分割の有無にかかわらず `scores` は候補全件（C-2 を壊さない） |

**起きてはいけないこと**

- 分割が有効なのに `arm` が記録されない → **実験データが復元できなくなる**
- 群の枠数が偏る（3対1 など）
- 割付が乱数の呼び出し順に依存する（再現不能になる）

## 8. 事前検証（イベント前に1回だけ回す）

**「実装が正しいか」ではなく「目的を果たすか」を確かめる。**
イベントは年1回なので、ここで問題を見つけられなければ手遅れになる。

### 8.1 埋め込み規則テスト — DRSA が正しく機能するか

**これが「DRSA が思いどおりに動くか」を確かめる決定打である。**

```
1. 合成データを作る。ただし「正解の規則」を意図的に埋め込む
     例: preference_match >= 3 なら 90% の確率で HIGH
         preference_match <= 1 なら 90% の確率で LOW
2. ノイズを混ぜる
3. DRSA にかける
4. 埋め込んだ規則が復元されるか確認する
```

手計算テスト（§5）は「部品が正しい」ことしか言わない。
これは**システムとして目的を果たすこと**を確認できる。

さらに**ノイズ率と件数を振って「地図」を作る。**

| 決定表の件数 | ノイズ 5% | ノイズ 20% | ノイズ 40% |
|---:|:-:|:-:|:-:|
| 30 | ? | ? | ? |
| 60 | ? | ? | ? |
| 120 | ? | ? | ? |
| 180 | ? | ? | ? |

各セルに「規則が復元されたか・γ はいくつか」を埋める。
**この表がそのまま品質ゲートのしきい値の根拠になる**（現状の 3本 / 0.5 / 0.5 は暫定値）。

### 8.2 当日シミュレーション — そもそも規則が出るのか

去年の来場分布・訪問間隔・評価回収率を使って当日を再現し、**次の1点**を確かめる。

> **DRSA は何時に、何人に対して、どんな品質で発火するのか。**

現状これは**去年データからの推定しかない**（[03-phases.md](03-phases.md) §4）。
実際に走らせて確認する。ここで「一日中 γ が 0.3 で規則が1本も出ない」と分かれば、
**イベント前に手を打てる**（属性の定義を変える、一貫性水準を見直す）。

**実装は `event-support-analytics` 側が適している**（去年データを持っているため）。

### 8.3 戦略の乖離度 — 実験が成立するか

**これを確認しないと、実験そのものが空振りする。**

`DRSA` と `COVERAGE` に**同じ入力**を与え、出てくる推薦順位を比べる。

```
順位相関 0.95 → ほぼ同じものを薦めている → A/B しても差が出ない
順位相関 0.3  → 明確に違うものを薦めている → 比較する意味がある
```

両者が似る理由はある。DRSA の主属性は `preference_match`（カテゴリ一致）で、
`COVERAGE` も `interest_term`（カテゴリ一致）を重み 0.5 で持っている。
**十分に似てしまう可能性がある。**

似すぎている場合の対策は「`W_INTEREST` を下げる」「DRSA 側の属性構成を見直す」。
**どちらもイベント前にしかできない。**

| # | 固定すること |
|---|---|
| S-1 | 同一入力に対する DRSA と COVERAGE の順位相関を測り、**記録する** |
| S-2 | `assigned` の重なり率（同じブースを何件選ぶか）を測る |
| S-3 | 相関が閾値（暫定 0.9）を超えたら**警告する**（自動失敗にはしない。判断材料） |

## 9. 性能

サーバー側のタイムアウトは既定 **1000ms**。超えると切られてフォールバックに落ちる。

| # | 固定すること |
|---|---|
| R-1 | 候補100件・規則100本で、応答が予算内（`RESPONSE_BUDGET_MS`、既定 600ms）に収まる |
| R-2 | **リクエスト処理中に規則生成・スナップショット取得が走らない** |
| R-3 | 予算を超えたら `COVERAGE` へ退避して 200 を返す |
| R-4 | 規則の再生成中もリクエストが処理できる（前回の規則を使う） |

**R-2 が最重要。** ここが崩れると当日のピーク（約9.3チェックイン/分）で全滅する。

## 11. テストデータ

**本番・去年の実データはテストに使わない。** 合成データのみを使う。

- `data/` に個人データを置かない。コミットしない
- サーバーの `sample-data/generate.ts` は
  `custom_answers` を UUID キーで書くため**そのままでは使えない**
  （[06-pre-survey-requirements.md](06-pre-survey-requirements.md) B-3）。
  合成データ生成はこちらで用意する
- **§8.1 の埋め込み規則テスト用に、「正解が既知の」生成器を用意する**
- 去年のデータ（`event-support-analytics`）は**推薦エンジンに食わせない**。
  ブース構成が毎年変わるため、**単一イベント完結が恒久的な設計制約**である

## 12. 当日リハーサル

単体テストで担保できないもの。

- `RECOMMENDER_URL` を未設定にしたまま、サーバー側の結合テストが通ること
- 推薦サービスを 500 にしても解放が成功すること
- 推薦サービスをタイムアウトさせても解放が成功すること
- 実際に飛んできたリクエストをログに出し、**`pre_survey` のキー名を目視確認する**
  （`age_range` / `age_group` のズレは実物を見るのが確実）
- **監視ダッシュボードを合成データで通しで動かす。**
  推薦エンジンを止めてフォールバック率が異常を示すことまで確認する
  （[10-observability.md](10-observability.md)）
- **JSONL ログの回収経路**（Cloud Logging → ファイル → 分析リポジトリ）を一度通す
- **キルスイッチ**（`PHASE_DRSA_MIN` の引き上げ）が効くこと
- **[11-deployment.md](11-deployment.md) §7 の確認項目（V-1〜V-16）を通すこと。**
  デプロイ直後に1回、当日リハーサルでもう1回。
  とくに V-2（`/ready` が 503 で正常）・V-5（`/demo` が 404）・V-14（Cloud Logging の構造化）
