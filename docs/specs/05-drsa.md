# DRSA コア — 優越関係・近似・規則生成

`drsa/` パッケージの実装仕様。**このモジュールは純粋である**（DB も HTTP も知らない）。
決定表を受け取り、規則を返す。それだけ。

## 0. 位置づけ

> **DRSA は「説明可能な選択フィルタ」として使う。精度最大化の予測器ではない。**

これは正本（Q-3）で決まっている。したがって設計上の優先順位は

1. **規則が人間に読めること**（研究発表で「なぜこのブースを薦めたか」を説明できる）
2. 少ないデータで壊れないこと
3. 精度

の順である。精度のために解釈性を捨てる変更はしない。

### なぜ通常のラフ集合ではなく DRSA なのか

条件属性も決定属性も**順序を持つ**（選好一致度が高いほど、評価も高いはず）。

通常のラフ集合は識別不能関係（indiscernibility）に基づくので、
「属性値が違う」としか言えず、**順序の矛盾を検出できない。**

DRSA は優越関係に基づくので、次のような矛盾を扱える。

```
x: preference_match=3, rating_affinity=3  →  評価 LOW
y: preference_match=2, rating_affinity=2  →  評価 HIGH

x は y を全属性で優越しているのに、評価が逆転している = 優越原理に反する
```

このような行は境界領域に落ち、確実規則の材料から外れる。
**「選好が一致しているのに低評価だった」という現象こそ観測したいもの**なので、
これを矛盾として明示的に扱えることが本質的である。

## 1. 用語と記法

| 記号 | 意味 |
|---|---|
| `U` | 決定表の全行（(参加者, ブース) ペアの集合） |
| `P` | 使用する条件属性の集合（`ENABLED_ATTRIBUTES`） |
| `Cl` | 決定クラス。本実装では `LOW` < `HIGH` の2クラス |
| `Cl_HIGH^>=` | 上方union。「HIGH 以上」＝ HIGH のみ |
| `Cl_LOW^<=` | 下方union。「LOW 以下」＝ LOW のみ |

すべての条件属性は**利得型（gain type）**とする。値が大きいほど「良い」向きに揃える
（[02-features.md](02-features.md) の属性はすべてそう定義してある）。

### 優越関係

```
x が y を P-優越する  ⇔  すべての q ∈ P について  x_q >= y_q
```

- `D_P^+(x) = { y ∈ U : y が x を P-優越する }`  （x を優越する側 = x 以上に良い行）
- `D_P^-(x) = { y ∈ U : x が y を P-優越する }`  （x に優越される側 = x 以下の行）

## 2. 近似

### 厳密版（参考）

```
下方近似  P_(Cl_HIGH^>=) = { x ∈ U : D_P^+(x) ⊆ Cl_HIGH^>= }
上方近似  P^-(Cl_HIGH^>=) = { x ∈ U : D_P^-(x) ∩ Cl_HIGH^>= ≠ ∅ }
境界領域  Bn = 上方近似 − 下方近似
```

下方近似は「この行以上に良い行が**すべて** HIGH である」＝確実に HIGH と言える領域。

### 実装は可変一貫性版（VC-DRSA）を使う

**厳密版は本件のデータでは実用にならない。**

条件属性2個・各3〜4値なのでパターンは12通りしかない一方、
評価は自己申告で強い個人差がある。**同じ属性値の組で HIGH と LOW が両方出るのは常態**であり、
厳密な下方近似はほぼ空集合になる。規則が1本も出ない。

そこで一貫性水準 `l`（`DRSA_CONSISTENCY`、既定 **0.8**）を導入する。

```
P_l(Cl_HIGH^>=) = { x ∈ U : |D_P^+(x) ∩ Cl_HIGH^>=| / |D_P^+(x)| >= l }
```

「この行以上に良い行のうち、8割以上が HIGH なら、確実側に入れてよい」とする。

- `l = 1.0` にすると厳密版に一致する。**テストで両方の挙動を固定する**
- `l` は設定値。**規則が0本になったら下げる**のではなく、
  **フェーズを下げる**のが正しい対応である（[03-phases.md](03-phases.md)）

### 近似の質

```
γ_P = |U − (すべての境界領域)| / |U|
```

`/ops/state` で公開する。**当日、DRSA がどれだけ機能しているかの唯一の直接指標**になる。

## 3. 規則の生成

### 規則の形

```
確実規則（上方）: if  preference_match >= 3  and  rating_affinity >= 2   then  評価 >= HIGH
確実規則（下方）: if  preference_match <= 1                              then  評価 <= LOW
```

- 上方規則は `>=`、下方規則は `<=` のみを使う。**混在させない**（DRSA の規則構文）
- 条件に現れない属性は「不問」

### 生成アルゴリズム — DOMLEM ではなく全列挙

正統的には DOMLEM（逐次被覆）を使う。**本実装では全列挙を採る。**

**理由: 探索空間が極小である。**

```
条件属性2個・各4値と3値 → 条件の候補は (4+1) × (3+1) = 20 通り（+1 は「不問」）
条件属性3個でも          → 5 × 4 × 4 = 80 通り
```

上方・下方あわせても数百通り。決定表が数百行なので、**全列挙しても一瞬で終わる。**
DOMLEM の逐次被覆はヒューリスティックであり結果が入力順に依存するが、
全列挙は**決定的**で、**再現性**（[01-io-contract.md](01-io-contract.md) §6）と相性が良い。

> 探索空間が爆発する属性構成に変えるときは、この判断を見直すこと。
> 目安として条件の候補が 10,000 を超えたら DOMLEM へ切り替える。

### 手順

```
1. 条件の候補をすべて列挙する（各属性のしきい値 × 「不問」）
2. 各候補について決定表を走査し、support / confidence を数える
      support    = 条件に合致する行数
      confidence = そのうち結論クラスに属する行の割合
3. MIN_SUPPORT（既定 5）未満、DRSA_CONSISTENCY（既定 0.8）未満を捨てる
4. 冗長な規則を落とす（§3.1）
5. 規則 id を付ける（安定 id。§3.2）
```

`MIN_SUPPORT = 5` は正本のしきい値の根拠（「各パターン最低5件」）と同じ値である。
**片方だけ変えないこと。**

### 3.1 冗長な規則を落とす

規則 A の条件が規則 B の条件より**緩い**（A が覆う行が B を包含する）とき、
`confidence(A) >= confidence(B)` なら **B を捨てる。**
条件が厳しいのに精度が上がらない規則は、説明として無価値である。

結果として残るのは**極小規則の集合**になる。

### 3.2 規則 id は安定させる

`reason.rules[].id` は研究データに残り、後から突き合わせる。

```
id = "R:" + sha1(結論の向き + 条件の正規化文字列)[:8]
```

**規則の内容が同じなら、再生成しても同じ id になること。**
連番にすると、5分ごとの再生成で id が入れ替わり、後から追跡できなくなる。

## 4. 規則の適用

```
候補ブースの条件属性ベクトル a に対して
  適合する上方規則 = 条件をすべて満たすもの
  適合する下方規則 = 同上
  → スコアへの集約は 04-strategies.md §4
```

計算量は `O(候補数 × 規則数)`。候補40件・規則100本でも問題にならない。

**適合規則が0本の候補は珍しくない。** その扱いも
[04-strategies.md](04-strategies.md) §4 で定義済み（`score = 0.5` + COVERAGE を低い重みで混合）。

## 5. キャッシュ

> **解放が最大3回に増えたため、呼び出しのたびに決定表を作り直すと間に合わない。**
> DRSA の規則は全体データから作るもので参加者ごとに変わらないので、
> 推薦エンジン側で一定間隔でキャッシュする。 — 契約の正本より

| 項目 | 既定 | 備考 |
|---|---|---|
| 再生成間隔 | 300 秒（`RULE_CACHE_TTL_SEC`） | スナップショット取得と同じ周期 |
| 実行場所 | バックグラウンドタスク | **リクエスト経路では絶対に生成しない** |
| 失敗時 | **前回の規則を保持し続ける** | 空にしない。古い規則のほうが無いよりましである |
| 起動直後 | 規則なし = `SIMILARITY` へ退避 | `/ready` が false を返す |

再生成のたびに `rules_built_at` を更新し、**全出力行に刻む**。

### 複数インスタンスについて

各インスタンスがプロセス内にキャッシュを持つため、
**同時刻に別々の規則が適用されうる**（生成タイミングがずれるため）。

`rules_built_at` を全行に刻んであるので、**後から識別・除外できる。**
単一インスタンス運用が前提なので実害は無い見込みだが、
研究上の再現性に関わるため記録で担保する。

## 6. テストで固定すること

### 手計算できる小さな決定表で検証する

```
preference_match  rating_affinity  →  decision
       3                 3               HIGH
       3                 2               HIGH
       2                 2               HIGH
       2                 1               LOW
       1                 1               LOW
       0                 2               LOW
```

- 優越集合 `D^+` / `D^-` が手計算と一致する
- 下方近似・上方近似・境界領域が手計算と一致する
- `l = 1.0` で厳密版と一致する
- 優越原理に反する行（上位が LOW、下位が HIGH）を1行足すと、境界領域に落ちる
- 規則 id が再生成しても変わらない

### 起きてはいけないこと

- 決定表が空・1行・全部同じクラスのときに例外を投げる
- 規則が0本のときに `phase='DRSA'` を返す（[03-phases.md](03-phases.md)）
- リクエスト処理中に規則生成が走る
- 規則の生成が入力の順序で変わる（決定性の破れ）
- `confidence` が高いだけで `support` が1〜2の規則が残る
