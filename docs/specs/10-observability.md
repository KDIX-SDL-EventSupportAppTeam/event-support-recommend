# 観測 — 推薦エンジンが外へ出すもの

**ダッシュボードの仕様は本リポジトリの管轄ではない。**
当日の監視画面と事後の分析画面は `event-support-analytics` が実装する
（`docs/specs/recommendation-evaluation/`）。

本ファイルが定義するのは、**推薦エンジン側が提供する観測データ**だけである。

---

## 1. 監視は推薦エンジンに依存させない（最重要）

> **推薦エンジンが死んでいるとき、推薦エンジンの `/ops/state` も死んでいる。**

したがって当日の監視は、**DB を主たる情報源とする。**

幸いサーバーが `card_unlock_events.strategy` に
「推薦が使えたか（`RECOMMEND`）／フォールバックしたか（`FALLBACK_COVERAGE`）」を記録している。
**DB を読むだけで推薦エンジンの生死が分かる。**

`/ops/state`（γ・規則数など推薦エンジンしか知らない値）は**補助**として使い、
取得できなければ「取得不能」と表示して他は動き続ける作りにする。

| 情報源 | 何が分かるか | 落ちたら |
|---|---|---|
| **DB**（`card_unlock_events` / `recommendation_scores` ほか） | 推薦が使えたか、フェーズ、決定表件数、割当の分布 | 監視自体が成立しない（が、その時はアプリも止まっている） |
| `/ops/state` | γ、規則数、規則の被覆率、応答時間 | **表示を落として続行する** |
| JSONL ログ | 入出力の全体、規則の本体 | 事後分析でのみ使う |

## 2. `/ops/state` が返すもの

当日の監視と事後の突き合わせに使う。**認証は `OPS_TOKEN`。書き込みは行わない。**

```jsonc
{
  "engine_version": "0.3.1",
  "snapshot": {
    "built_at": "2026-10-16T04:35:00Z",
    "ok": true,
    "decision_table_size": 214,
    "participants": 137,
    "booths": 40
  },
  "rules": {
    "built_at": "2026-10-16T04:35:00Z",
    "count_certain_up": 4,          // 「>= HIGH」を結論する確実規則
    "count_certain_down": 3,        // 「<= LOW」
    "gamma": 0.62,                  // 近似の質
    "candidate_coverage": 0.71,     // 直近リクエストで規則が当たった候補の割合
    "consistency_level": 0.8
  },
  "phase": {
    "current": "DRSA",
    "quality_gate_passed": true,
    "gate_detail": { "size": true, "rules": true, "gamma": true, "coverage": true },
    "next_threshold": null
  },
  "experiment": {
    "split_active": true,           // 参加者内ランダム化が発動しているか
    "split_started_at": "2026-10-16T04:40:00Z"
  },
  "latency_ms": { "p50": 38, "p95": 112, "budget": 600 },
  "requests": { "last_30min": 214, "errors_last_30min": 0 }
}
```

**`gamma` と `candidate_coverage` は推薦エンジンしか知らない。**
「DRSA と判定されているのに、実は規則が当たっていない」を検出する唯一の手段である。

## 3. JSONL ログ（事後分析用）

推薦1回につき1行、標準出力へ。Cloud Logging に残す。

| 種別 | 1行の意味 | 用途 |
|---|---|---|
| `recommend` | 1回の推薦の入出力の全体 | 事後のリプレイ・個票の再構成 |
| `rules_built` | 規則の再生成1回ぶん（**規則の本体を含む**） | 「その時刻にどんな規則が存在したか」の復元 |
| `snapshot_built` | スナップショット取得1回ぶんの要約 | 決定表の成長曲線 |

### `rules_built` を必ず残す理由

規則は5分ごとに作り直される。**その時点でどんな規則が存在したかは後から復元できない。**

`recommendation_scores.reason_payload` には規則 **id と要約しか入らない**
（3万行になるため本体は入れられない）。
**このログが無いと、論文に「実際に抽出された規則」を載せられなくなる。**

### ログの回収経路まで用意する

Cloud Logging の中でしか読めない状態は、実質使えないのと同じである。

```
gcloud logging read → JSONL ファイル → event-support-analytics
```

**この経路をイベント前に一度通しておく。** 当日の夜に初めて試すことにしない。

## 4. 当日、監視すべき項目と対応行動

**表示はダッシュボード側の仕事だが、「何を見て何をするか」はこちらが定義する。**
対応行動の無い数字は当日画面に載せない。

| 指標 | 情報源 | 異常 | 対応 |
|---|---|---|---|
| **フォールバック率**（直近30分） | DB | 30%超 | 推薦エンジンのログ確認・再起動。**最優先** |
| **評価回収率** | DB | 25%未満 | 運営に声かけを依頼（**当日打てる数少ない手**） |
| 現在フェーズ / 次まで残り | DB | 15時でも COVERAGE | 決定表が育っていない。原因を追う |
| **γ・確実規則の本数** | `/ops/state` | γ が低い / 規則0〜1本 | 品質ゲートが正しく止めているか確認 |
| 規則の被覆率 | `/ops/state` | 低い | 大半の候補が判断保留（`score=0.5`）になっている |
| 応答時間 p95 | `/ops/state` | 600ms 超 | タイムアウト（1000ms）が近い |
| **割当されたブースの集中度** | DB | 特定ブースに集中 | **人気順への退化。全戦略の禁止事項の実地検出** |
| 空マス（`booth_id IS NULL`） | DB | 発生 | 候補切れ（E7） |

### キルスイッチ

当日おかしいと気づいたときに手を打てる状態にしておく。

| 手段 | 効果 |
|---|---|
| `PHASE_DRSA_MIN` を極端に大きくする | DRSA を止めて SIMILARITY へ落とす |
| `PHASE_SIMILARITY_MIN` も上げる | COVERAGE のみで運用する |
| `RECOMMENDER_URL` を空にする（サーバー側） | 推薦を完全に切り離す。**最終手段** |

**設定を変更したら、変更時刻を必ず記録する。**
前後を別データとして扱わないと分析が壊れる（[09-research-design.md](09-research-design.md) R-2）。

## 5. 当日に見てはいけないもの

> **A/B の効果（DRSA 枠と COVERAGE 枠の訪問率の差）を当日に表示しない。**

見ると「DRSA のほうが悪いから設定を変えよう」という判断をしたくなる。
それをやると**実験が壊れる。** 無意識にやってしまうのが怖い。

- ✅ 表示してよい：各群の**提示数**（分割が半々に機能しているかの確認）
- ❌ 表示しない：訪問率の**差**

効果は当日の行動に何も影響しないので、隠しても失うものが無い。

## 6. 個票（1人の物語）の再構成

事後に、参加者1人の全体を時系列で並べられるようにする。
**集計が正しくても個票が変なら実装がおかしい**ので、サニティチェックとして機能する。

再構成に必要なものは、DB と JSONL に揃っている。

| 要素 | 情報源 |
|---|---|
| アンケート回答 | `user_survey_answers` |
| カードの状態遷移 | `bingo_cells` / `card_unlock_events` |
| 何が推薦されたか・スコア・条件属性 | `recommendation_scores` |
| **どちらの群の枠か** | `recommendation_scores.attributes.arm` |
| 訪問・評価 | `check_ins` / `booth_ratings` |
| **どの規則が発火したか** | `reason_payload.rules[].id` ＋ `rules_built` ログ |

**匿名 ID のまま扱う。** 実装は `event-support-analytics` 側。
