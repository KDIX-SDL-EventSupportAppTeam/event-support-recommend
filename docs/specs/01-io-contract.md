# 入出力の定義 — このサービスが何を受け取り、何を返すか

**HTTP 契約の正本は `event-support-server` の
`docs/specs/bingo-dynamic-unlock/05-recommender/contract.md` である。**
[ADR 0004](https://github.com/KDIX-SDL-EventSupportAppTeam/event-support-server/blob/develop/docs/decisions/adrs/0004-split-recommender-repository.md)
の決定により、本リポジトリは契約の内容をコピーせずリンクで参照する。

本ファイルが定義するのは、契約の写しではなく次の3つである。

1. 契約の**どこが固定で、どこが自由か**（＝アルゴリズムを何度作り替えても壊れない境界）
2. 契約の外側から**追加で取りに行くデータ**の定義（入力の上限）
3. アルゴリズムが見る**内部ドメインモデル**（戦略の差し替え単位）

## 0. 設計の前提

このリポジトリは**アルゴリズムを何度も作り替える**ことを前提とする。
そのための構えは次の一文に集約される。

> **出力の形は固定し、入力は取れるだけ取る。
> 可変部分は「サーバーが解釈せずそのまま保存する2つのフィールド」に閉じ込める。**

呼び出し元は推薦の中身を一切解釈しない。したがってアルゴリズムの変更が
サーバー・フロント・DB スキーマに波及することは**構造的にありえない**。
唯一の制約は、後述する `attributes` / `reason` の**自己記述性**である。

---

## 1. 責務の境界

| 担当 | 内容 |
|---|---|
| **このサービスがやる** | 候補ブースの順位づけ、条件属性の算出、フェーズ判定、規則の生成とキャッシュ、研究用の生データ生成 |
| **このサービスがやらない** | 解放処理そのもの、DB への書き込み、マスへの割当、指標（セレンディピティ率など）の計算、UI への表示 |

**このサービスは書き込みを一切行わない。** 応答が遅い・落ちる・誤った値を返す、のいずれでも
呼び出し元はフォールバックで解放を完遂する。**壊しうるのは推薦の質と研究データの質だけ**であり、
アプリの動作は壊せない。この非対称性が、アルゴリズムを大胆に差し替えてよい根拠になる。

---

## 2. 入力

入力は**3層**ある。層1だけが契約で固定されており、層2は自分で取りに行く。

```
┌─ 層1: リクエスト（契約で固定・1リクエストごと・その参加者の情報だけ） ─┐
│   POST /recommend/cells                                                │
└────────────────────────────────────────────────────────────────────────┘
┌─ 層2: イベントスナップショット（自分で取得・5分キャッシュ・全参加者分） ─┐
│   決定表・規則・統計の材料。入力の主戦場はこちら                        │
└────────────────────────────────────────────────────────────────────────┘
┌─ 層3: 内部ドメインモデル（層1＋層2を正規化したもの） ───────────────────┐
│   アルゴリズムはこれだけを見る。HTTP も SQL も知らない                  │
└────────────────────────────────────────────────────────────────────────┘
```

### 2.1 層1 — リクエスト（変更できない）

フィールドの定義は契約の正本を見ること。ここには**実装から観測した事実**だけを記す。

| 観測した事実 | 出典 | 実装上の含意 |
|---|---|---|
| `pre_survey` は専用列（`age_range` / `occupation` / `industry`）に `custom_answers` を展開してマージした平坦な辞書 | `assignOuterCells.ts` `buildPreSurveyPayload` | 関心分野は `interest_categories`（`category_id` の配列）としてトップレベルに現れる |
| 年代のキーは **`age_range`**。契約の例文にある `age_group` は飛んでこない | `survey.ts` / `presurveyApi.ts` | `age_range` を正とし、`age_group` は後方互換としてのみ読む |
| `visited_booths` は **`is_achieved = 1` のカードのマスのみ** | `buildVisitedBoothsPayload` | カード外訪問（`cell_id IS NULL`）は入ってこない |
| `source` で事前推薦マスと自由訪問を区別できる | 同上 | 事前推薦マスの訪問を選好の証拠にすると推薦が自己増幅する。**行動由来の選好は `FREE_VISIT` のみから作る** |
| `candidate_booths` が空なら**そもそも呼ばれない** | `assignOuterCells.ts` | 候補ゼロの分岐は不要 |
| `rating` は 0〜3 件しか付かない。`rating_scale` は可変 | 契約 / `RATING_SCALE` | 高評価・低評価の判定はスケール比で正規化する |

**層1に「無い」もの（層2で補う対象）**

- 他の参加者の訪問・評価（＝**決定表そのもの**）
- カード外訪問（推薦なしの自発訪問。研究の対照群）
- ブースの説明文・タグ・名称（来るのは `category_id` だけ）
- カテゴリの名称、イベントの日程、現在時刻の基準
- 過去にこの参加者へ何を推薦したか

### 2.2 層2 — イベントスナップショット（取得経路は未確定）

**取得経路は未決定であり、本ファイルはその「形」だけを先に固定する。**
経路が DB 直読みでも、サーバーの追加 API でも、**層3から見た姿は同一**になるよう抽象化する
（`data/repository.py` の 1 インターフェース）。決定は別途 ADR に残す。

取得したい範囲は「アルゴリズムを作り替えても足りなくならない」ことを基準に、広めに取る。

| 対象 | 取りたい項目 | 用途 |
|---|---|---|
| `booths` | id, category_id, is_active, name, description | 候補の属性。将来テキスト特徴を使う余地 |
| `booth_tags` | booth_id, tag | カテゴリより細かい粒度。**契約には来ない** |
| `categories` | id, name | 関心分野との突き合わせ |
| `check_ins` | user_id, booth_id, visit_order, checked_in_at, cell_id | 全参加者の訪問。`cell_id IS NULL` がカード外訪問＝対照群 |
| `booth_ratings` | user_id, booth_id, checkin_id, rating, scale, rated_at | **決定表の決定属性** |
| `user_survey_answers` | user_id, age_range, occupation, industry, custom_answers | 条件属性・類似度軸 |
| `users` | id, role | **`role <> 'participant'` を全集計から除外する** |
| `bingo_cells` | card_id, booth_id, source, is_achieved | 推薦済み・訪問済みの把握 |
| `card_unlock_events` | card_id, phase, strategy, created_at | 自分の過去の挙動の確認 |
| `recommendation_scores` | user_id, booth_id, score, was_assigned | 同一参加者への推薦の重複回避、当日の自己診断 |
| `events` | date_start, date_end | 時間帯特徴を使う場合の基準 |

**取得してはならないもの**: `users.email`、`users.password_hash`。
推薦にも分析にも不要であり、渡さないことをもって事故を構造的に防ぐ。

**更新頻度**: 既定5分（`SNAPSHOT_TTL_SEC`）。リクエスト経路の外で更新する。
規則の生成は全体データから行うもので参加者ごとに変わらないため、この間隔で足りる。

### 2.3 層3 — 内部ドメインモデル

アルゴリズムが見る唯一の型。**層1と層2の由来を隠蔽する**ので、
取得経路が変わっても戦略のコードは変更されない。

```
RecommendationContext
├── request:     RequestContext    # cell_count, exclude_booth_ids, candidates, 受信時刻
├── participant: Participant       # user_id, survey, visits[], ratings[]
├── snapshot:    EventSnapshot     # booths, categories, decision_table, rules, stats, built_at
└── config:      RuntimeConfig     # しきい値・有効属性・スケール比

Strategy.recommend(ctx) -> list[ScoredBooth]   # 候補「全件」を返す。1件も落とさない
```

戦略（`COVERAGE` / `SIMILARITY` / `DRSA` / フォールバック）はすべてこの1インターフェースを実装する。
**フォールバックも戦略の1つとして扱う**（例外処理の分岐ではなく、選択肢の1つにする）。

## 3. 出力

**形は契約で固定されている。正本を参照すること。**
ここでは「実装が必ず守る不変条件」と「唯一の拡張口の使い方」を定義する。

### 3.1 必ず守る不変条件

| # | 不変条件 | 破ったときに起きること |
|---|---|---|
| O-1 | `decision_table_size` は **snake_case** で数値を返す | camelCase だと `null` として記録され、データ量と精度の関係が永久に分析できなくなる |
| O-2 | `scores` は `candidate_booths` の**全件**を含む。1件も落とさない | 落とした行はサーバーが `score=null` / `interest_match='UNKNOWN'` で埋める。「推薦が沈黙した」のか「手を抜いた」のかが区別できず、セレンディピティ率の分母が壊れる |
| O-3 | `interest_match` は 4 値のいずれか。判定可能なのに `UNKNOWN` を返さない | 同上。研究データが丸ごと使えなくなる |
| O-4 | `assigned` は `cell_count` 以下。足りなくてよい。**無理に埋めない** | 苦し紛れに人気ブースで埋めるくらいなら、サーバーのフォールバックに任せたほうが記録が正確になる |
| O-5 | 返す `booth_id` は必ず `candidate_booths` 内のもの | 候補外はサーバーに破棄される |
| O-6 | **どんな入力でも 200 を返す。500 を返さない** | レスポンスが無いとサーバーは `phase='COVERAGE'` / `decision_table_size=null` を記録する。本当は DRSA が使えた時間帯だったという事実が復元できなくなる |
| O-7 | `score` は**同一リクエスト内でのみ比較可能**な相対値（0..1）とする | フェーズが違えばスコアの意味も違う。**リクエストを跨いだ score の直接比較は無効**。分析側はこれを前提にすること |

**O-6 の帰結**: 例外は握りつぶし、COVERAGE 相当の結果を返す。
ただし `phase` は「実際に使えた戦略」を返すので、
「DRSA が使えたはずの時間帯に COVERAGE が返っている」＝異常として後から検出できる。

### 3.2 唯一の拡張口 — `attributes` と `reason`

サーバーが永続化するのは次の6つだけである（`recommendation_scores`）。

```
score / rank_in_event / was_assigned / interest_match / attributes / reason_payload
```

**トップレベルに独自フィールドを足しても保存されない**（パーサが読まないため無視される）。
したがってアルゴリズムの変更を後から解釈するための情報は、
すべて `attributes` / `reason` に入れるしかない。**この2つが唯一の拡張口である。**

この2つはサーバーが中身を解釈せずそのまま JSON として保存するので、
形を変えてもサーバー・DB・フロントの変更は一切不要。**契約を変えずにいくらでも拡張できる。**

### 3.3 拡張口の作法（これだけは規律として守る）

自由なぶん、**後から読めなくなる**のが唯一の失敗モードである。次を必ず守る。

**(1) 自己記述であること。** 何のバージョンの、どの戦略が、どの属性構成で出した値かを、
行だけ見て判別できるようにする。

```jsonc
"attributes": {
  "v": 1,                                 // このスキーマのバージョン
  "strategy": "DRSA",                     // 実際に値を作った戦略
  "enabled": ["preference_match", "rating_affinity"],  // 有効だった条件属性の構成
  "condition": {                          // 条件属性の値（凍結値）
    "preference_match": 3,
    "rating_affinity": 2
  },
  "raw": {                                // 属性を組み立てた材料。再計算・検証用
    "declared": 2, "behavioral": 1,
    "category_id": "…", "visitor_count": 12
  }
}
```

```jsonc
"reason": {
  "v": 1,
  "strategy": "DRSA",
  "rules": [                              // 適用された規則。規則本体は入れず id と要約だけ
    { "id": "R12", "class": ">=high", "support": 14, "confidence": 0.86 }
  ],
  "tie_break": "visitor_count_asc",
  "engine": { "version": "0.3.1", "rules_built_at": "2026-10-16T04:35:00Z" }
}
```

**(2) 属性構成の変更は `v` を上げる。** 条件属性を足す・意味を変えるときは
`attributes.v` を上げ、`docs/specs/02-features.md` に旧版の定義を残す。
当日にしきい値や属性構成を変えても、行ごとにどの定義で計算されたか判別できる状態を保つ。

**(3) 小さく保つ。** 1推薦あたり候補約40件、参加者250人 × 3回で**約3万行**が生成される。
1行あたり数百バイトを上限の目安とし、規則の本文・決定表・候補一覧を各行に入れない
（それらは自前ログに1回だけ出す。§5）。

**(4) 意味を後から変えない。** 一度使ったキー名の意味を変えるより、新しいキーを足す。
過去の行を再解釈する必要が出た時点で、研究データとしての価値が落ちる。

## 4. エンドポイント

| メソッド | パス | 呼ぶ人 | 用途 |
|---|---|---|---|
| POST | `/recommend/cells` | **サーバー（契約）** | 推薦。これが本体 |
| GET | `/health` | インフラ | 生存確認。依存なしで即答する |
| GET | `/ready` | インフラ | スナップショット・規則が温まっているか |
| GET | `/ops/state` | 運営・開発（要トークン） | 現在のフェーズ、決定表件数、規則数、最終更新時刻、直近の応答時間 |
| POST | `/ops/rebuild` | 運営・開発（要トークン） | スナップショットと規則の強制再生成（当日の緊急対応） |
| POST | `/ops/replay` | 開発（要トークン） | 保存済みリクエストを再実行して出力を比較する。アルゴリズム変更時の回帰確認 |

- サーバーが呼ぶのは `/recommend/cells` だけ。それ以外を増やしても契約に影響しない
- `/ops/*` は `OPS_TOKEN` で保護する。書き込みを行わないので、最悪でも情報の露出に留まる
- `/ops/replay` は「アルゴリズムを何度も作り替える」前提に対する備え。
  本番同等の入力で新旧の出力差分を見られるようにする

## 5. 自前ログ（入力を取れるだけ取っておくための保険）

**推薦1回につき、入力と出力の全体を JSONL で1行、標準出力へ吐く。**

- 保存先は Cloud Logging。DB には書かない（このサービスは書き込みを行わない）
- サーバー側の `recommendation_scores` への書き込みが失敗しても、**こちら側に完全な記録が残る**
- 3万行の JSON をサーバーの DB に押し込めない情報（規則本体・決定表の要約・候補全件の中間値）は、
  ここに 1 リクエスト 1 回だけ出す
- `user_id` は元から仮名。メールアドレス等は層2で取得しないので、ログにも入り得ない

**イベントは年1回、1日だけである。取らなかったデータは二度と取れない。**
取りすぎたログは無視すればよいだけなので、迷ったら出す。

---

## 6. 再現性

アルゴリズムを作り替える以上、**同じ入力から同じ出力が出ること**を確認できる必要がある。

- 同順位の並べ替えに乱数を使うが、**シードは `hash(user_id, unlock 文脈)` で決める**。
  参加者ごとにばらけつつ、同じ入力なら同じ結果になる
- `engine.version` と `rules_built_at` を全行に刻む
- `/ops/replay` で、保存済み入力に対する新旧の出力を突き合わせる
