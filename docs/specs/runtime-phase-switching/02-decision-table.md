# 決定表の組み立て

取得した行から DRSA の決定表を作る。**ここは純関数にする**（`data/` と `drsa/` の間の変換）。
DB にも HTTP にも触れない。合成データでテストできること。

## 1行が意味するもの

**1行 = 「ある参加者が、あるブースを訪問し、評価した」という1件の事実。**

```
(条件属性ベクトル, 決定クラス)
```

- 条件属性は [02-features.md](../02-features.md) の定義をそのまま使う（`features/` を呼ぶ）
- 評価が無い訪問は**行にならない**。決定属性が無いため
- したがって **`decision_table_size` = 評価済みチェックインの件数**（ロールは問わない。出展者・運営スタッフも含む）

## 条件属性

有効なのは既定の2個（[ADR 0003](../../decisions/adrs/0003-条件属性の構成.md)、`ENABLED_ATTRIBUTES`）。

| 属性 | 出どころ | 値域 |
|---|---|---|
| `preference_match` | 事前アンケートの関心分野 × ブースのカテゴリ | 順序尺度 |
| `rating_affinity` | その参加者のそれまでの評価履歴との親和度 | 順序尺度 |

**`exploration_disposition` は既定で無効のまま**（[02-features F-1](../02-features.md)）。
[ADR 0009](../../decisions/adrs/0009-当日の切り替えは既定値のまま走らせ調整は事後に行う.md) に従い、
今回は有効化しない。

**年代・性別・職業を条件属性にしない。** これらは `SIMILARITY` の近傍軸としてのみ使う。

## 決定クラス

`features/rating.py` の `normalize_rating` と `classify_decision` をそのまま使う。

- 評価を `rating_scale`（既定4）で正規化する
- `HIGH_RATING_RATIO`（0.75）以上を HIGH、`LOW_RATING_RATIO`（0.25）以下を LOW
- 中間は**どちらでもない**行として扱う（決定表には載るが、上方・下方どちらの union にも入らない）

## 時間の扱い

**決定表は「その時点までに評価されたもの」で作る。** 未来の評価は入らない。
5分ごとに作り直すので、当日は自然に育っていく。

### 行ごとの属性は、その行より前の情報だけで計算する（2026-10-10, issue #38）

各行の `rating_affinity`・`preference_match` は、**その参加者のその行より前のチェックイン**
（`checked_in_at` → `checkin_id` 順）の自発訪問・高評価・低評価だけから作る。
推薦は「いま知り得ること」で属性を作るので、学習側も同じ時点の情報だけを使う。

| 属性 | 推薦時 | 決定表（修正後） |
|---|---|---|
| 関心一致度 | 自発訪問カテゴリの +1 を足す（0〜3） | **同じ（+1 を足す）。** 以前は足さず 0〜2 だった |
| 低評価の履歴 | ★1 だけ（`normalized <= 0.25`） | **同じ（★1 だけ）。** 以前は★1〜3 だった |
| 評価履歴の時点 | 推薦時点まで | **同じ（その行より前だけ）。** 以前はその行より後の評価も使っていた |

計算は `features.history_signals` を推薦時（`strategies/common.py`）と共有する。ずれを構造で防ぐ。

**自発訪問 (`source = FREE_VISIT`) の出どころ**: `check_ins` には `source` が無いので、
`bingo_cards`（参加者 ↔ カード）→ `bingo_cells`（ブースごとの `source`）から引く。
この 2 テーブルは**任意取得**で、取れなくてもスナップショットは成立する
（自発訪問の信号が立たない = 以前と同じ 0〜2 に戻るだけ）。読み取り専用ユーザーには SELECT 権限が付与済み
（`event-support-analytics/deploy/sakura-readonly-proxy/grant.sql`）。

**`exploration_disposition` は決定表に載せない。** `ENABLED_ATTRIBUTES` に入れても無視する
（人の属性は同じ人の候補ブースでは値が同じで順位付けできない。以前は有効化すると全行が落ちて決定表が空になった）。

### 基準率

決定表全体の HIGH（★4）の割合と LOW（★1〜3）の割合を `RuleCache` に入れる。
品質ゲートのリフト条件（[03-phases.md](../03-phases.md) §3.3）の比較基準になる。

**過去のイベントの評価を混ぜてはならない。** 去年のデータには評価が存在せず、
仮に存在しても参加者もブースも異なる。イベント単位で閉じる。

## 除外

- `booths.is_active = 0`（取り下げられたブース）
- 同一参加者 × 同一ブースの重複行（`uq_rating_per_checkin` があるので通常起きないが、防御的に畳む）

## 規則の生成

決定表ができたら `drsa/` の既存の純関数を順に呼ぶだけ。**新しいアルゴリズムは書かない。**

```
approximate(table, DRSA_CONSISTENCY)   → 上方・下方近似
gamma(table, DRSA_CONSISTENCY)         → 近似の質 γ
generate_rules(...)                    → RuleSet（確実規則の上方・下方）
```

生成した結果は `RuleCache.put(ruleset, decision_table_size=..., gamma=...)` に入れる。

## 規模の見積もり

去年の実績（チェックイン約1200件）と評価回収率の想定から、
**当日の決定表は最大でも数百行**である。規則生成は毎回ゼロから作り直してよい
（増分更新の複雑さを持ち込まない）。5分間隔に対して十分速い。

**もし想定を超えて遅くなった場合も、リクエスト経路には影響しない。**
バックグラウンドが1周に5分以上かかるようになるだけで、その間は前回の規則が使われる。

## 「起きてはいけないこと」

- **評価が無い訪問を「評価0」として行にすること。** 未評価と低評価は違う。
  混ぜると「評価しなかった人が多いブース」が低評価に見える
- **決定表を全イベント横断で作ること**
- **`visitor_count`（人気度）を条件属性に入れること。** 人気ブースの推薦に退化する
