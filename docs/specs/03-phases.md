# フェーズ判定 — データ量に応じた戦略の切替

> **2026-10-10 の方針確定（[ADR 0010](../decisions/adrs/0010-ランダムからDRSAとセレンディピティ規則へ切り替える.md)）で、自動モードの段階は
> 「ゲート不通過の間は完全ランダム → 品質ゲート通過後は DRSA」になった。**
> **`SIMILARITY` と `COVERAGE`（訪問者が少ない順）は自動モードでは使わない。**
> 契約の `phase` は 3 値のままなので、ランダム期は `phase = COVERAGE` を返し、
> 実際に使った戦略は `reason.strategy`（`RANDOM`）で区別する。
> 本文のうち `SIMILARITY` を挟む記述（§1 の表の一部・§4 の試算・§6 の境界値の一部）は、
> この方針で上書きされる。ゲートの値は §3.3 が正。

**正本は `event-support-server` の
`docs/specs/bingo-dynamic-unlock/05-recommender/phases.md`。**
本ファイルは実装側の解釈と、しきい値の扱いを定義する。

## 0. なぜこの仕組みがあるのか

> **去年の最大の失敗は、フォールバックの解除が早すぎたことである。**

累計チェックイン約60件（1ブース1.5人）で解除され、推薦は事実上
**ブース人気度ランキングに退化**した。上位は飲食ブースと制作チーム自身のブースで、
誰にでも当たる推薦になり、研究目的に一切寄与しなかった。

**フェーズ判定は精度を上げるための仕組みではなく、
「データが足りないのに賢いふりをする」ことを構造的に禁じるための仕組みである。**
迷ったら**上げない**側に倒す。

## 1. 3つのフェーズ

| フェーズ | 条件 | 戦略の要旨 |
|---|---|---|
| `COVERAGE` | ゲート不通過（決定表 < `PHASE_DRSA_MIN` を含む） | **完全ランダム**（`reason.strategy = RANDOM`。契約の `phase` は `COVERAGE`） |
| `SIMILARITY` | （自動モードでは使わない。自動ラダーに入らない） | — |
| `DRSA` | `PHASE_DRSA_MIN` 以上 **かつ品質ゲート通過**（§3.3） | DRSA 規則による推薦。使えなければ静かにランダムへ戻る |

戦略の中身は [04-strategies.md](04-strategies.md)。

**判定は推薦のたびに行う。** 同じ参加者でも1回目の解放はランダム、
3回目は `DRSA` ということが起こる。**想定どおりの挙動である。**

---

## 2. 決定表の件数（`decision_table_size`）の定義

**フェーズを決める唯一の入力**であり、サーバーの `card_unlock_events` にも記録される。

```
decision_table_size = [02-features.md §1.2 の条件をすべて満たす行の件数]
```

具体的には、そのイベントにおいて

- 評価が付いている `(参加者, ブース)` のペアであり
- 参加者が `role = 'participant'` であり
- 参加者が事前アンケートに回答済みである

ものの件数。**「評価件数」とは厳密には一致しない**ことに注意する。

### 測れなかった場合は `null` を返す（`0` ではない）

| 状況 | `decision_table_size` | `phase` |
|---|---|---|
| 決定表を構築でき、0件だった | `0` | `COVERAGE` |
| **スナップショットを取得できず、構築を試みられなかった** | **`null`** | `COVERAGE` |

**「0件だった」と「測れなかった」を区別する。**
`null` は「この時刻に推薦エンジンがデータへ到達できていなかった」という記録になり、
当日の障害を後から特定できる。0 を返すとその事実が消える。

> なおサーバー側は、こちらが応答しなかった場合も `phase='COVERAGE'` /
> `decision_table_size=null` を記録する。**200 を返して `null` を報告するほうが、
> 500 で落ちるより情報量が多い**（[01-io-contract.md](01-io-contract.md) O-6）。

## 3. しきい値

**コードに直書きしない。設定値として外に出す**（Q-2 は未確定）。

```
PHASE_SIMILARITY_MIN=30
PHASE_DRSA_MIN=60          # 条件属性2個での既定値。§3.1 を参照
```

### 3.1 `PHASE_DRSA_MIN` は属性の個数に連動する

正本の 180 という数字の根拠は明示されている。

```
条件属性3個 → 4 × 3 × 3 = 36 パターン × 各5件 = 180件
```

**ところが暫定の属性構成は2個である**（[02-features.md](02-features.md)）。
同じ根拠で計算すると

```
条件属性2個 → 4 × 3 = 12 パターン × 各5件 = 60件
```

となり、**正本の 180 とは3倍ずれる。** 正本の 180 は、予備の第3属性
（年代・性別など）を有効にした構成を前提に置かれた数字である。

| `ENABLED_ATTRIBUTES` | パターン数 | `PHASE_DRSA_MIN` |
|---|---:|---:|
| `preference_match`, `rating_affinity` | 12 | **60**（既定） |
| ＋ `exploration_disposition` | 36 | **180** |

**属性構成を変えたら、しきい値も必ず一緒に変える。**
片方だけ変えると、パターンあたりの件数が枯れて規則が1人の気まぐれを写す。

30 / 60 件で埋め込み規則がどれだけ復元されるかの測定は
[07 §8.1](07-testing.md) の地図（`tools/build_prevalidation_map.py`）にある。
**決定（2026-10-10）: `PHASE_DRSA_MIN=60` を採用する。** `PHASE_SIMILARITY_MIN=30` は
自動モードでは使われなくなった（`SIMILARITY` を自動ラダーから外したため）。
決定を人間の判断なしに変えてはいけない（`AGENTS.md` 禁止6）。

### 3.2 `PHASE_SIMILARITY_MIN` の 30 は根拠が弱い（自動モードでは使わない）

正本も「似た参加者を数グループに割るために最低限必要な件数の目安」としか書いていない。
**そのまま 30 を使うが、根拠が弱いことを認識しておく。**

幸い、正本が示すとおり**しきい値の精度は挙動をほとんど左右しない**。
去年のデータでは、評価回収率が 25% でも 60% でも切替時刻は 45分の幅にしか動かない。
13:30 前後にチェックインが集中する（2時間で全体の 72.6%）ためである。

**分析コストを割く価値は低い。設定値として外に出しておけば実務上は十分。**

### 3.3 `DRSA` への昇格は件数だけで決めない（品質ゲート）

**決定表が60件あっても、まともな規則が出ているとは限らない。**

規則が0本、あるいは1本だけで `support` が下限ぎりぎり、という状態でも
「決定表60件」の条件は満たしてしまう。その状態で `DRSA` に昇格すると、

- 規則が当たらないので候補の大半が判断保留（`score = 0.5`）になり、
  **実質 `COVERAGE` と同じ結果を返しながら、記録上は `DRSA` になる**
- 参加者内ランダム化（[09-research-design.md](09-research-design.md)）を発動すると、
  **中身が同じもの同士を比較することになり、少ない標本を無駄にする**

そこで昇格条件を、**すべて満たすこと**とする。

```
DRSA へ昇格する条件（AND）

1. 決定表の件数          >= PHASE_DRSA_MIN      （既定 60）
2. 有効な確実規則の本数  >= DRSA_MIN_RULES      （既定 2）
     有効 = 上方・下方合わせて、確信度 − 基準率 >= DRSA_MIN_LIFT（既定 0.10）のもの
     基準率 = 上方規則なら決定表全体の★4率、下方規則なら★1〜3率
3. 近似の質 γ            >= DRSA_MIN_GAMMA      （既定 0.5）
4. 規則が候補を覆う割合  >= DRSA_MIN_COVERAGE   （既定 0.5）
```

**決定（2026-10-10, [ADR 0010](../decisions/adrs/0010-ランダムからDRSAとセレンディピティ規則へ切り替える.md)）: 上の値が RD-2 の決着である。**

- **リフト条件の理由**: γ は予測力を測らない。★4 を付けやすい会場では、好みと無関係な
  「どの条件でも高評価」という偽の規則が確信度だけでゲートを通る。確信度が全体の基準率を
  上回ること（= 条件に意味があること）を要求して防ぐ。シミュレーションで誤作動 48〜68% → 数 % に下がった
- **上下合わせて数える理由**: 旧実装は上方（高評価向き）だけで数えており、条件属性が実質 1 つで
  最大 2 本前後しか出なかった。旧設定では解放の 0〜4% しか DRSA が動かなかった
- 高評価は **★4 のみ**（★3 以上にすると誤作動 9〜10%）

- **γ が低い＝データが優越原理に矛盾しており、規則が信用できない。** 門番として適切
- 4 は「直近のリクエストで、適合規則が1本以上あった候補の割合」
- **どれか1つでも欠けたらランダムに留まる。** 判定結果は `/ops/state` に出す
- **しきい値はすべて設定値。** ただし §3.1 と同様、根拠なく下げないこと

> **規則が出ないからといってゲートを下げてはならない。**
> （新しい値は本番前に入れ、当日は触らない — [ADR 0009](../decisions/adrs/0009-当日の切り替えは既定値のまま走らせ調整は事後に行う.md)）
> それは「解除が早すぎた」という去年の失敗の再現である
> （[09-research-design.md](09-research-design.md) R-3）。出ないなら出ないと報告する。

**参加者内ランダム化は実施しない**（RD-1 の決定。[09-research-design.md](09-research-design.md)）。
ゲートを通過した時刻は引き続き記録し、前後を別データとして扱えるようにする。

## 4. 誰がどのフェーズを受けるか（去年データからの推定）

> **2026-10-10 以前の試算（`SIMILARITY` を挟む構成）。** 新構成では `SIMILARITY` の行は「ランダム」と読み替える。
> 新構成のシミュレーションでは、ラフ集合（DRSA 期）が関わる解放は 1 日の約 55〜57%、
> 開始は 13:00 前後だった（[ADR 0010](../decisions/adrs/0010-ランダムからDRSAとセレンディピティ規則へ切り替える.md)）。

参加者は訪問2件目・3件目・4件目で解放を受ける。訪問間隔の中央値は 3.4分なので、
**3回の解放は来場から15〜30分の間に集中する。**

| 初回ログイン | 人数 | 1回目 | 2回目 | 3回目 |
|---|---:|---|---|---|
| 11:00 | 15 | COVERAGE | COVERAGE | COVERAGE |
| 12:00 | 15 | SIMILARITY | SIMILARITY | SIMILARITY |
| 13:00 | 25 | SIMILARITY | SIMILARITY | SIMILARITY〜DRSA |
| **13:30** | **43** | SIMILARITY〜DRSA | DRSA | DRSA |
| 14:00 | 31 | DRSA | DRSA | DRSA |
| 15:00 | 23 | DRSA | DRSA | DRSA |

- DRSA が3回とも効く: 約 97名（64%）
- 一度も効かない: 約 30名（20%）

**これは去年のデータに基づく推定であり、確定値ではない。**
また上表は `PHASE_DRSA_MIN = 180` を前提とした正本の試算である。
既定の 60 で運用すると **DRSA への到達はこれより早くなる。**

> **早まることの是非は、当日の監視で判断する。**
> 「去年の失敗＝解除が早すぎた」を繰り返さないため、
> 迷ったら `PHASE_DRSA_MIN` を上げる側に倒す。設定値なので当日でも変更できる。

## 5. 記録

サーバーが `card_unlock_events` に保存する。こちらは値を返すだけで、書き込まない。

- `phase` — **実際に使えた戦略**を返す。判定結果ではない
- `decision_table_size` — §2 の定義

この2つが揃うと、**フェーズごとの踏破率・満足度を比較できる。**
「データ量が増えると推薦が良くなる」という主張の直接の証拠になる。

**判定は `DRSA` でも、規則が1本も出なければ実際には推薦できない。**
その場合は下位の戦略へ落ち、**`phase` には実際に使った戦略名を返す**
（[04-strategies.md](04-strategies.md) §5）。判定結果を返すと、
記録上は DRSA なのに中身は COVERAGE、という解釈不能な行ができる。

## 6. テストで固定すること

> `decide_phase` は自動モードでは `COVERAGE`（ランダム）と `DRSA` しか返さない。
> `PHASE_SIMILARITY_MIN` は使われない（`strategies/registry.py` の自動ラダーにも入らない）。

境界値は純関数として固定する。

| 入力 | 期待 |
|---|---|
| 29 | `COVERAGE` |
| 30 | `COVERAGE`（`SIMILARITY` を使わない） |
| 59 | `COVERAGE` |
| 60（ゲート通過） | `DRSA` |
| 60（ゲート不通過） | `COVERAGE`（ランダムに留まる） |
| 0 | `COVERAGE`（例外を投げない） |
| 負数・NaN・None | `COVERAGE`（例外を投げない） |
| `PHASE_DRSA_MIN` を設定で変更 | 即座に反映される。`PHASE_SIMILARITY_MIN` は結果に影響しない |
| `ENABLED_ATTRIBUTES` に3個目を足す | `PHASE_DRSA_MIN` の既定が 180 になる |

**品質ゲート（§3.3）**

| 入力 | 期待 |
|---|---|
| 件数は足りるが有効な規則が 1 本（`DRSA_MIN_RULES=2`） | ランダムに留まる |
| 確信度 − 基準率 = 0.099 の規則しか無い（`DRSA_MIN_LIFT=0.10`） | ランダムに留まる |
| ★4 を付けやすい会場の偽の規則（確信度 ≈ 基準率） | ランダムに留まる |
| 上方 1 本・下方 1 本（リフト 0.10 以上） | 通過（上下合わせて 2 本） |
| 件数・規則は足りるが γ = 0.4（`DRSA_MIN_GAMMA=0.5`） | ランダムに留まる |
| 件数・規則・γ は足りるが被覆率 0.3 | ランダムに留まる |
| 4条件すべて満たす | `DRSA`。`quality_gate_passed = true` |
| ゲート通過の可否 | `/ops/state` に項目別（`gate_detail`）で出る |

**起きてはいけないこと**

- しきい値がコードに直書きされていて設定で変えられない
- 決定表が空なのに `SIMILARITY` 以上を返す
- **規則が0本なのに `phase='DRSA'` を返す**
- **確信度が基準率に届かない（リフトの無い）規則でゲートを通過する**
