# パラメータ調整と監視の置き場所

**推薦のパラメータ調整画面（`/demo`）と当日監視を `event-support-analytics` に集約できるか**を検討したもの。
[11-deployment.md](../11-deployment.md)（デプロイ）とは**別の議題**として分けてある。デプロイはこれの決着を待たない。

| ファイル | 扱う範囲 |
|---|---|
| [11-deployment.md](../11-deployment.md) | Cloud Run へ出すこと。**確定済み** |
| 本ファイル | 調整画面と監視をどこに置くか。**未決定** |

---

## 0. 前提 — 監視はすでに analytics 側にある

新しく作る話ではない。**設計としても実装としても、監視は既に analytics が担っている。**

- [10-observability.md](../10-observability.md) §1 が「**監視は DB を主たる情報源とし、`/ops/state` は補助**」と定めている
- `event-support-analytics` に `🚦 推薦の当日監視`（`src/live_dashboard.py`）が実装済み。
  `OpsStateClient`（`src/rec_db.py`）は取得失敗時に例外を投げず「取得不能」表示へ落とす
- analytics は Cloud Run へデプロイ済み。合言葉（`DASHBOARD_PASSWORD`）で保護されている
- **読み手が運営メンバーからエンジニアへ切り替わった**（2026-08-31・analytics の `AGENTS.md`）。
  画面の前提条件がこちらに有利な方向へ変わっている

したがって論点は「監視を移すか」ではなく、**残っている `/demo`（パラメータ調整）をどうするか**である。

## 1. `/demo` の実態（コードで確認した事実）

| 論点 | 事実 | 根拠 |
|---|---|---|
| 本番の設定を書き換えられるか | **できない。** 呼ばれるたびに新しい `Settings` を組み立てるだけで `app.state.settings` に触らない | `demo.py:98` `_settings()` |
| overrides は任意の値を通せるか | 通せない。既知キー・範囲内に丸める | `demo.py:78` `sanitize_overrides()` |
| 何をしているか | 合成シナリオ6件に対し `run_recommendation()` を実行する | `demo.py:257` |
| **副作用** | **`run_recommendation()` は JSONL ログを出力する** | `engine.py` `_log_recommend()` |

**「パラメータをいじられる」ことは問題ではない。本番には反映されないからである。**
問題は最後の1行にある。

## 2. 最大の問題 — `/demo` は研究ログの汚染源である ★

> `/demo/run` を1回叩くたびに、`kind: "recommend"` のログが
> `user_id: "u_alice"` `"u_bob"` … （`demo.py:191` 以降の合成 ID）で観測ログへ流れ込む。

[ADR 0006](../../decisions/adrs/0006-推薦サービスを未認証で公開する.md) は
未認証公開の最大リスクを「偽リクエストによる JSONL ログの汚染」と評価した。
**その最も叩きやすい入口が `/demo` 自身**だった、というのが本検討で判明した最も重要な事実である。

さらに悪い点が2つある。

1. **第三者が叩かなくても起きる。** 当日エンジニアが自分でパラメータを試した分が、そのまま本番ログに入る
2. **置き場所を変えても解決しない。** analytics へ移しても、計算を推薦本体で行う限り同じことが起きる。
   **これはホスト先の問題ではなく、`run_recommendation()` がログを出すという構造の問題である**

### 影響範囲（切り分け）

| 対象 | 汚れるか | 理由 |
|---|---|---|
| 当日の監視ダッシュボード | **汚れない** | DB（`card_unlock_events`）を主情報源にしているため（[10-observability.md](../10-observability.md) §1） |
| **事後分析の JSONL** | **汚れる** | 合成 ID の推薦記録が本物と同じ `kind` で混ざる |
| 本番の推薦挙動 | 変わらない | §1 のとおり設定を書き換えない |

`user_id` が固定値（`u_alice` など）なので DB の参加者一覧との突合では落ちる。
**しかし「落とせるから放置してよい」ではない。** 分析側に、こちらの都合による除外処理を持たせることになる。

### 対応案（P-1）

**先に決めるべきはこれで、置き場所（§3）より優先度が高い。**

| 案 | 内容 | 評価 |
|---|---|---|
| **a** | `kind` を `"recommend_demo"` に分ける | ⭐️ **推奨。** 「出さない」より「区別できる形で出す」ほうが、後から何が起きたか復元できる |
| b | `run_recommendation(..., emit_log=False)` でログを抑止する | ○ 単純だが、誰がいつ何を試したかが残らない |
| c | 何もしない | ❌ 分析側に除外責務を押し付ける |

**未決定 P-1: a か b か。** 決まるまで `/demo` を本番へ出さない。

## 3. `/demo` の置き場所（未決定 P-2）

**§2 の P-1 が片付いていることが前提。** 片付いていれば、どの案でも安全に選べる。

| 案 | 内容 | コスト | 難点 |
|---|---|---|---|
| **A** | 推薦側に残し `OPS_TOKEN` で保護する。analytics の画面からリンクを貼る | **ほぼゼロ** | 秘密が2つになる（合言葉・`OPS_TOKEN`）。画面は完全には1枚にならない |
| **B** | UI を analytics（Streamlit）に作り、計算は推薦側の新エンドポイント（`POST /ops/simulate`、中身は既存の `/demo/run`）に投げる | 中 | 760行の UI を書き直す。**計算の正本は1つのまま保てる** |
| **C** | analytics が推薦パッケージを import して `strategies/` を直接呼ぶ | 中 | ❌ **採らない。** §5 X-3 を参照 |

**「エンジニアが1箇所を見れば済む」という目的は、A のリンク1本でも達成できる。**
真に1画面へ寄せたいなら B。判断材料は「760行を書き直す価値があるか」だけである。

**未決定 P-2: A か B か。**

## 5. 起きてはいけないこと

| # | 禁止 | 破ると |
|---|---|---|
| **X-1** | 調整画面を「本番設定の変更手段」として扱う | 反映は Cloud Run の env（＝新リビジョン）だけ。**混同すると当日に事故る** |
| **X-2** | **画面から本番パラメータを書き換える経路を作る** | [10-observability.md](../10-observability.md) §5 が「A/B の効果を当日見るな」と定めている。見ながら変えられる画面は、**実験そのものを壊す**。利便性と引き換えにしてよいものではない |
| X-3 | analytics が推薦パッケージを import して `strategies/` を直接呼ぶ（§3 案 C） | バージョンずれで「画面の結果と本番の結果が違う」が起きる。**二重管理は [AGENTS.md](../../../AGENTS.md) 禁止2 と同じ失敗の形** |
| X-4 | 監視の主情報源を `/ops/state` に移す | **推薦エンジンが死んでいるとき `/ops/state` も死んでいる**（[10-observability.md](../10-observability.md) §1） |
| X-5 | P-1 を未決のまま `/demo` を本番へ出す | 研究ログが汚れる。§2 |

**`features/` を analytics が import することは禁止ではない**（[08-architecture.md](../08-architecture.md) §1 のとおり、むしろ想定された使い方）。
X-3 が禁じているのは `strategies/`（＝推薦の結果そのもの）を二重に持つことである。
