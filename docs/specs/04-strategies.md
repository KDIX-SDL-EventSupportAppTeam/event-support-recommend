# 推薦戦略 — 3つのフェーズの中身

各フェーズで実際に何をするかを定義する。フェーズの選び方は [03-phases.md](03-phases.md)。

## 0. 全戦略に共通する不変条件

**この節は、どの戦略を新しく足すときも必ず守る。**

| # | 不変条件 | 理由 |
|---|---|---|
| S-1 | **候補全件にスコアを付けて返す。1件も落とさない** | `scores` が研究の分母になる（[01-io-contract.md](01-io-contract.md) O-2） |
| S-2 | **人気順に退化しない。** スコアと `visitor_count` の順位相関が正になってはならない | このアプリの成功の定義は踏破率ではない。**去年の失敗の再現を構造で禁じる** |
| S-3 | 例外を投げない。情報が無ければ「無関係」側へ倒す | 開場直後は入力がほぼ空。それは異常ではなく通常 |
| S-4 | 戦略は HTTP も SQL も知らない。`RecommendationContext` だけを見る | 取得経路が変わっても戦略のコードは変わらない |
| S-5 | 同スコアの並べ替えは `visitor_count` 昇順 → シード付き乱数 | 全員に同じマスが配られるのを防ぎつつ、再現性を保つ |

### S-2 について（このリポジトリで最も重要な制約）

> **人気ブースを全員に薦めれば踏破率は上がるが、それは失敗である。**

去年、フォールバックの解除が早すぎた結果、推薦は事実上ブース人気度ランキングに退化し、
上位は飲食ブースと制作チーム自身のブースだった。誰にでも当たる推薦であり、
研究目的に一切寄与していない。

**混雑度・訪問者数を「高いほど良い」向きで使ってはならない。**
使ってよいのは、同スコアの並べ替えで**空いているほうを優先する**ときだけである。

## 1. インターフェース

```
Strategy.recommend(ctx: RecommendationContext) -> list[ScoredBooth]

ScoredBooth = {
  booth_id, score(0..1), attributes, reason
}
```

- 返すのは**候補全件**。`assigned` の選抜は戦略の外（§4）で行う
- `score` は**同一リクエスト内でのみ比較可能**な相対値。
  フェーズを跨いだ比較は無効（[01-io-contract.md](01-io-contract.md) O-7）
- フォールバックも戦略の1つとして実装する。**例外処理の分岐にしない**

## 2. `COVERAGE` — 訪問者数が少ない順 ＋ 関心分野一致

データが無い時間帯の**正規の戦略**であり、同時に全フェーズの**最終退避先**でもある。

### スコア

2つの項の重み付き和とする。**どちらの項も `visitor_count` に対して単調非増加**である。

```
coverage_term = 1 - rank(visitor_count 昇順) / (候補数 - 1)     # 訪問者が少ないほど高い
interest_term = { MATCH: 1.0, PARTIAL: 0.6, MISMATCH: 0.2, UNKNOWN: 0.2 }

score = W_COVERAGE * coverage_term + W_INTEREST * interest_term   # 既定 0.5 / 0.5
```

- **重みは設定値**（`W_COVERAGE` / `W_INTEREST`）
- `interest_term` の `MISMATCH` を 0 にしない。**0 にすると不一致ブースが構造的に選ばれなくなり、
  セレンディピティが観測できなくなる**
- 事前アンケート未回答なら `interest_term` は全候補 `UNKNOWN` になり、
  実質「訪問者数が少ない順」だけが残る。これは正しい退避である

### 不変条件

- **同じ `interest_term` を持つ候補どうしでは、`visitor_count` 昇順に厳密に並ぶこと**
- 全体としてスコアと `visitor_count` の順位相関が**負であること**（テストで固定する）

> サーバー側のフォールバックは関心分野を考慮しない「訪問者数が少ない順」だけである。
> **こちらが 500 を返すより COVERAGE を返すほうが良い**のは、この一項ぶん賢いからである。

## 3. `SIMILARITY` — 属性が似た参加者が高評価したブース

決定表は育っていないが、参加者を数グループに割る程度の件数はある段階。

### 近傍の作り方

事前アンケートの回答から距離を測る。**ここで年代・性別・職業が働く**
（条件属性としては使わないが、類似度軸としては有効。[02-features.md](02-features.md) §2）。

| 軸 | 距離の測り方 | 既定の重み |
|---|---|---|
| `interest_categories` | Jaccard 係数 | 0.5 |
| `age_range` | 一致 / 不一致 | 0.2 |
| `occupation` | 一致 / 不一致 | 0.2 |
| `exploration_disposition` | 順序距離（1段差=0.5, 2段差=1.0） | 0.1 |
| `gender` | **使わない** | — |

**`gender` を近傍の軸に入れない。** 去年の分布では「その他」が3名であり、
これを軸にすると近傍が個人を指しうる。層別の集計軸としてのみ扱う。

上位 `SIMILARITY_NEIGHBORS`（既定 20）人を近傍とする。

### スコア

近傍がそのブースに付けた評価の平均を、**件数で全体平均へ縮約する**（ベイズ縮約）。

```
score = (Σ normalized_rating + M * global_mean) / (n + M)     # M = SIMILARITY_SHRINKAGE、既定 5
```

- **縮約は必須である。** これが無いと「近傍1人が高評価した」だけのブースが最上位に来る。
  評価が1人あたり 0〜3 件しか付かない以上、これは頻繁に起きる
- 近傍の評価が1件も無いブース（`n = 0`）は `global_mean` に落ちる。
  **その状態で全候補が同点になるのを避けるため、`COVERAGE` のスコアを
  低い重み（`SIMILARITY_COVERAGE_FLOOR`、既定 0.2）で混ぜる**
- **`visitor_count` は一切スコアに入れない。** 混ぜると人気度が復活する（S-2）

## 4. `DRSA` — 規則による推薦

### 実行時にやること

**規則の生成は行わない。** キャッシュ済みの規則を、その参加者の候補に当てはめるだけ。
生成はバックグラウンドで一定間隔（既定5分）に行う（[05-drsa.md](05-drsa.md)）。

```
1. 候補ごとに条件属性ベクトルを作る          # features/ を呼ぶ
2. 適合する規則を集める
3. スコアへ集約する
4. 適合規則の id と要約を reason に入れる
```

### スコアへの集約

規則は「上方union `>= HIGH` を結論するもの」と「下方union `<= LOW` を結論するもの」に分かれる。

```
up   = 適合した「>= HIGH」規則の confidence の最大値（無ければ 0）
down = 適合した「<= LOW」規則の confidence の最大値（無ければ 0）

score = (1 + up - down) / 2        # 0..1 に収まる
```

- **適合規則が1本も無い候補**は `score = 0.5`（判断保留）とし、
  `COVERAGE` のスコアを低い重み（`DRSA_COVERAGE_FLOOR`、既定 0.2）で混ぜて順序を付ける。
  **全候補にスコアを付ける義務（S-1）を満たすため**
- `reason.rules` には**規則 id と要約だけ**を入れる。規則本体は入れない（3万行になるため）

## 5. 退避（degradation）

**上位フェーズが実行できないときは、静かに下位へ落ちる。落ちた事実は `phase` に出す。**

```
DRSA ──規則が0本／規則キャッシュが未構築──▶ SIMILARITY
SIMILARITY ──近傍が作れない／スナップショット無し──▶ COVERAGE
COVERAGE ────────────────────────────────▶ 必ず成功する（層1の情報だけで動く）
```

**`phase` には「判定結果」ではなく「実際に使った戦略」を返す。**
判定は DRSA だが中身は COVERAGE、という行が残ると解釈不能になる。

`COVERAGE` は層1（リクエスト）の情報だけで完結するので、
**スナップショットが一切取得できない状況でも必ず結果を返せる。**
これが「500 を返さない」（O-6）を実現の裏づけである。

## 6. `assigned` の選抜

戦略が返した全候補のスコアから、マスに載せる分を選ぶ。**戦略の外側の共通処理**とする。

```
1. score 降順に並べる
2. 同点は visitor_count 昇順 → シード付き乱数（S-5）
3. 上位 cell_count 件を取る
4. exclude_booth_ids・重複を除く（サーバーも弾くが、こちらでも弾く）
```

- **足りなくても無理に埋めない**（O-4）。サーバーのフォールバックに任せたほうが記録が正確になる
- シードは `hash(user_id, unlock 文脈)`。参加者ごとにばらけつつ、同じ入力なら同じ結果になる

### 同一カテゴリの偏り（既定では対策しない）

`cell_count = 6` のとき、上位6件がすべて同じカテゴリになることは起こりうる。

**既定では制限しない。** 正本が
「意図的なセレンディピティ戦略は実装せず、DRSA が素直に選んだ結果に
不一致ジャンルが混ざるのを観測する」と定めているため、
人為的な多様性制約は観測対象を歪める。

ただし**偏りが実際に起きるかは自前ログで観測できる**ようにし、
上限を設ける場合に備えて設定だけ用意しておく（`MAX_PER_CATEGORY`、既定 無効）。
**有効化するかは実データを見てから判断する**（§8 T-1）。

## 7. 戦略を追加するときの手順

このリポジトリはアルゴリズムを何度も作り替える前提である。

1. `Strategy` を実装する（候補全件を返す）
2. §0 の不変条件、特に **S-2（人気順への退化禁止）のテスト**を書く
3. `attributes.strategy` / `reason.strategy` に戦略名を入れる
4. 条件属性の意味を変えたなら `attributes.v` を上げる（[02-features.md](02-features.md) §6）
5. `/ops/replay` で旧戦略との出力差分を確認する

**サーバー・DB・フロントの変更は一切不要である。**
